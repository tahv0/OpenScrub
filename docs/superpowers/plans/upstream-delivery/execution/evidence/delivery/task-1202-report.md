## Behavior and ownership

The new stdlib-only `openscrub_internal.job_logs.JobLog` retains at most **2,000 entries / 524,288 UTF-8 payload bytes per job**, with **8,192 bytes per entry including `... [message truncated]`**. The limits remain unchanged after calibration. One callback, including embedded newlines, owns one absolute position. Plain strings only are accepted; unsupported objects and string subclasses raise a fixed TypeError without conversion. Lone surrogates become `?`. Normalization encodes a prefix of at most 8,192 codepoints rather than encoding/copying the full oversized input, and truncation ends on a UTF-8 codepoint boundary.

One deque of bounded strings/sizes, byte count, absolute base/next, epoch and truncation counter is protected by one local lock. Normalization happens before lock admission, eviction before append, and snapshots detach bounded lists/scalars under that lock. JSON encoding occurs after unlocking. The leaf retains no job, invokes no callbacks, acquires no job/vault/file lock, writes no files and exposes no list facade or clear primitive. Constructor seeding is incremental.

All three constructors now install a store before publication: ordinary `new_job`, incomplete-upload recovery, and report/output recovery. The twelve ordinary append owners remain in place, including repaired-option notes, manual tracking, scan/render, thumbnail completion, worker errors, cancellation/retry and watchdog failure. Retry keeps its store/epoch and appends its existing marker. Independent desktop, updater and installer log owners are unchanged.

A producer ownership regression exposed a concrete existing trigger: a thumbnail closure scheduled for an old job could begin after `JOBS[jid]` had been replaced, look up the replacement and append there. The closure now captures the original job. The event/deferred-thread regression verifies the original store receives its thumbnail message and the replacement remains untouched, then exercises actual manual-tracking detector/sample/completion callbacks. No thumbnail scheduling, decoder, file/publication or lease protocol was added.

## Cursor and client contract

`len` and metadata `log_len` remain absolute next positions, including evicted entries. `/log` returns `{from,lines,len,epoch,base,reset,dropped,truncated}` from one snapshot. Every interval satisfies `base <= from <= len` and `lines.length == len-from`. Request epoch mismatch wins over stale, which wins over future; each reset replays retained history. In-range requests return their suffix. Negative cursors normalize to zero; malformed or overlong cursors return a fixed bounded 400 (`from` max64 characters, optional epoch max128).

For retained `[100,103)` in epoch E1, `from=101&epoch=E1` returns two entries, `from=20` returns all three with `reset=stale`, and `from=999&epoch=E1` returns all three with `reset=future`. A replacement E2 returns retained E2 history with `reset=epoch`, even if its new absolute next has already exceeded the old cursor. Numeric-only clients cannot detect every replacement.

Metadata's tail of 30, absolute next, epoch/base/retained/bytes/dropped/truncated fields come from one tail snapshot. They remain advisory to P03: only a complete, validated log snapshot advances accepted cursor/epoch. Any new-schema field requires the complete schema, bounded epoch, safe nonnegative integer positions/counters, exact interval and consistent reset reason. Explicit legacy handling retains old-backend shrink/refetch and authoritative empty behavior.

Initial and reset snapshots replace the transcript with their latest 400 entries. Ordinary same-epoch suffixes append once; fixed omission/truncation/replacement notes sit outside sequence data. Existing view/cycle fences, every post-await ownership guard, single flight, 15-second body deadline, abort/backoff, hidden-page recovery, scroll-up behavior and save/review state remain. Incremental browser transcript retention remains P12C work.
