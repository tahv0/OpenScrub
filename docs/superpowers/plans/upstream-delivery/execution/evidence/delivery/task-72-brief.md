### Identity and server contract

1. A new identified addition carries `manual_id`, an opaque case-sensitive ASCII string matching `[A-Za-z0-9._:-]{1,128}`. IDs are scoped to the job's logical review report. Omitted ID retains legacy append behavior; an explicitly invalid/null/empty/non-string ID receives HTTP 400 with a JSON error while the job is otherwise eligible for edits. Never deduplicate different IDs or legacy additions by equal coordinates. Unknown unrelated data remains preserved.
2. Persist the ID plus `manual_creation` in the appended raw detection, in the same existing report transaction. The immutable creation record has exactly the effective normalized fields `t_start`, `t_end`, `cbox`, `aoff`: existing numeric time normalization, integer content-space box conversion, default `t_ref=t_start` and existing fps/cum reference-offset selection. Preserve the existing normalization algorithm; raw fractional boxes/reference times producing the same effective creation are equivalent. Identified creation needs finite time/coordinate/offset numbers, a four-coordinate box and a two-number offset so equality is well defined; retain existing interval/extent handling rather than importing P16C's render-validation work. Do not trust incoming client-supplied `manual_creation`; derive it server-side. Fixed category/text/confidence/default enabled/last_seen are existing server behavior, not new caller-controlled fields.
3. Replaying a matching ID and immutable creation record succeeds without appending or resetting the current row. Never compare against current cbox/times/enabled/last_seen: those may already contain valid later edits. Duplicate identical IDs in one payload follow the same rule; distinct IDs with identical effective creation append separately. Incompatible reuse returns HTTP 409 with a clear JSON error and leaves the whole request unapplied, including unrelated supplied edits.
4. An incoming ID matching multiple rows, or an identified imported row lacking a valid stored `manual_creation`, receives HTTP 409 with a clear JSON error without reconstructing creation from mutable current fields. Do not retroactively assign IDs, deduplicate or migrate legacy rows. Unrelated legacy/additive data must not block an otherwise valid ordinary edit merely because it lacks this new metadata.
5. Perform latest-document lookup, supplied indexed patches, replay checks/new appends and final publication under Task622's single per-job transaction. Conflict/validation failure releases locks/lifetimes without partial publication; simultaneous same-ID requests cannot append twice. No second global lock, durable request journal or external identity store. Preserve the existing success response shape unless a demonstrated supported flow requires an additive field.
6. This is a logical no-op for replayed creation. Skipping an otherwise unchanged report write/edited-state update belongs to P06C; do not grow this task into serialization optimization. IDs alone do not resolve stale requests across a replacement scan/report, and browser reload does not preserve current in-memory drafts; document those limits rather than claiming general recovery.
