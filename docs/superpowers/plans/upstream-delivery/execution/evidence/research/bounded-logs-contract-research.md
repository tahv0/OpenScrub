## One private store and justified limits

Add **`openscrub_internal/job_logs.py`** and minimal **`openscrub_internal/__init__.py`**. This leaf owns the nontrivial retention/cursor/concurrency invariant and can be tested with only stdlib imports, without Flask/OpenCV startup. That is a concrete reason for extraction. Preserve Python>=3.9: deque, threading.Lock and uuid suffice; avoid Python3.10+ union syntax/match/dataclass slots and newer typing-only dependencies. Do not introduce a generic logging framework, dependency, background consumer, persistence, diagnostics hook or callback-discovery machinery.

Proposed fixed defaults, to be calibrated during implementation rather than represented as measured costs:

| Bound | Proposed value | Rationale and limit of evidence |
| --- | --- | --- |
| Retained entries per job | 2,000 | Five times the existing initial400-entry display convention; gives a useful recent timeline beyond metadata30 while bounding entry/object counts. This is a proposed product choice, not an observed sufficient duration. |
| Sum of retained UTF-8 payload bytes | 512 KiB | Independent ceiling for long error/OCR callback strings; count alone permits arbitrarily large strings. At2,000 entries it permits about262 payload bytes on average before the byte ceiling dominates; this is arithmetic, not a measured message distribution. |
| One logical callback entry, including truncation suffix | 8 KiB UTF-8 | Allows substantial tool/error context while rejecting a single huge payload consuming the whole store. Preserves the entry's prefix and a fixed `... [message truncated]` suffix on valid codepoint boundaries. Needs representative synthetic/ordinary-output calibration. |

One callback invocation remains one sequence entry, even if its text contains newlines. Do not `splitlines()` into an unbounded intermediate list or normalize away message order. Thus “30/400 lines” retains its current practical meaning of30/400 callback entries; one entry can occupy multiple physical display lines. Preserve ordinary Unicode content. For oversized input, take at most8,192 Unicode codepoints first, encode that bounded prefix with UTF-8 replacement for lone surrogates, then trim bytes on a codepoint boundary to reserve the suffix. This avoids encoding/copying the full oversized input; the bounded prefix's temporary UTF-8 buffer can still be up to32 KiB. Use a fixed message for unsupported non-string input, without arbitrary `str()` conversion or callback inspection. The current producer contract is strings; existing P03 already rejects non-string response lines.

Use one `collections.deque` of `(bounded_text, utf8_size)` tuples plus total payload bytes, retained base, next sequence, epoch, eviction/truncation counters and one `threading.Lock`. No second all-history list, raw-message queue, string accumulator or cached unbounded serialization. `append` normalizes outside the lock, then under the lock evicts oldest entries until the projected count and byte total fit, appends, increments `next`, and updates `base = next - retained_count`. Eviction before append avoids even an internally over-budget deque. Preserve messages in lock-admission order; do not sort producer timestamps. Constructor seed messages are fed through append incrementally, never `list(iterable)`.

Expose `append(text)`, `snapshot(from_seq, epoch=None)`, `tail_snapshot(30)`, and an internal `clear()` primitive for explicit reset verification/future owners; **do not add a clear HTTP route or call clear on retry**. Snapshots return plain immutable-by-ownership values: fresh lists of retained bounded strings and scalar state, never the live deque. Do not define list-style slicing or ambiguous `__len__` as the public contract. Existing assertions use `snapshot(...).lines` instead of requiring a pretend list.

Each mutation/read acquires only this store lock. A complete snapshot copies at most2,000 references/512KiB of represented payload; tail metadata copies at most30 references. Perform `jsonify`/encoding after unlocking. Append is amortizedO(1) eviction; a worst-case append may evict up to2,000 entries. Copy cost and contention remain to be measured. Store code never acquires `JOBS_LOCK`, touches files or calls callbacks, so existing `JOBS_LOCK`→store-lock callers cannot invert lock order. No lock is held across network writes, engine work, waits, joins, file leases or vault work. This makes log fields mutually consistent, **not** an atomic transaction over every changing job phase/progress field or over the two separate HTTP requests.

## Absolute cursor and epoch contract

Within a published store, `next` counts every accepted entry, including ones evicted; retained entries occupy the contiguous interval `[base,next)`. `len` in `/log` and `log_len` in job metadata remain this absolute next position, **not retained count**. `from` is the actual first returned absolute position. Every response satisfies `base <= from <= len`, `lines.length == len - from`, and contains exactly that contiguous interval from one locked snapshot. A quiet in-range request at `next` returns empty lines and `from == len == next`.

Additive `/log` response fields: `epoch`, `base`, `reset` (`null`, `stale`, `future`, or `epoch`), `dropped`, `truncated`; retain `from`, `lines`, `len`. Metadata retains last30 `log_tail` and absolute `log_len`, adding `log_epoch`, `log_base`, `log_retained`, `log_bytes`, `log_dropped`, `log_truncated` from **one** tail snapshot. Counters contain no message contents. `truncated` counts accepted oversized messages in the current epoch; `dropped` counts evictions in that epoch. Do not synthesize marker entries on every eviction: that would consume sequence numbers, displace useful messages and potentially recurse. Show a fixed UI note from these counters and reset reasons.

The query gains optional `epoch=<internally generated opaque token>`. Generate a fresh bounded token (for example existing stdlib `uuid.uuid4().hex`) for a new store or explicit clear, never persist it. Apply rules under the same snapshot lock, in this priority order:

1. A supplied epoch differs: return retained `[base,next)`, `reset='epoch'`.
2. Requested nonnegative cursor `< base`: return `[base,next)`, `reset='stale'`.
3. Requested cursor `> next`: return `[base,next)`, `reset='future'`.
4. Otherwise return `[requested,next)`, `reset=null`.

Keep the existing negative-cursor normalization to0. Return a bounded400 JSON error for malformed/noninteger `from`, rather than letting `int(...)` produce a500; cap the cursor query at64 characters before conversion and an optional epoch query at128 characters. These are proposed parser limits, not measured performance thresholds. Unknown query fields are ignored. A no-epoch caller retains the old request shape and old numeric meanings, and sees explicit additive reset/clamp information. **Unchanged P03 cannot accept a nonempty stale clamp**: at2318 it requires `nl.from === LOGN`. Compatibility means updating the shipped client in this PR; it cannot promise an untouched old browser knows the new overflow semantics. No-epoch legacy callers also cannot detect same-length replacement; a numeric cursor alone contains insufficient information.

Illustrative responses below show synthetic sequence labels, not recorded callback contents. Suppose epoch`E1`, base100, next103, entries`M100,M101,M102`:

| Request / action | Atomic result and client effect |
| --- | --- |
| `?from=101&epoch=E1` | `{from:101,len:103,base:100,epoch:E1,reset:null,lines:[M101,M102]}`; append once and advance to103. |
| `?from=20&epoch=E1` | `{from:100,len:103,base:100,epoch:E1,reset:stale,lines:[M100,M101,M102]}`; reset displayed transcript to returned retained history and show “Earlier log messages were omitted.” Advance to103. |
| `?from=999&epoch=E1` | Same retained history, `reset:future`; replace display and advance to103. Starting at the end would silently discard new history. |
| `?from=103&epoch=E1` | `{from:103,len:103,base:100,epoch:E1,reset:null,lines:[]}`; no duplicate entries. |
| Explicit internal `clear()` | Keep next103, empty storage, base103, fresh epoch`E2`; reset eviction/truncation counters for the new epoch. An old`E1` request returns `{from:103,len:103,base:103,epoch:E2,reset:epoch,lines:[]}` and clears the client. |
| Append after that clear | New entry owns sequence103, next104. An`E2/from103` request returns that entry once. A concurrent clear/append/read linearizes under the store lock, so each append is wholly before or after clear and each snapshot belongs wholly to one epoch. |
| Retry without clear | Append retry marker at103 in`E1`, next104, same epoch and history subject to ordinary eviction. Existing view reopen asks from0, receives stale clamp if needed, then displays latest400 entries. |
| Fresh-process rehydration | New store starts base0/next1 with its recovery entry and fresh`E3`. `?from=103&epoch=E1` gets reset epoch and recovery history. Even if new history has already grown beyond103 before the old tab polls, epoch mismatch forces replay rather than silently skipping it. |

Keep one store object attached to each live job; do not assign a replacement into an already published job. Recovery creates a new job/store before registration. This avoids background callback references retaining detached stores. The clear primitive is a log reset, not a cancellation fence: an append racing clear is admitted on whichever side obtains the lock. P12B does not add operation cancellation semantics. If a future owner needs to exclude old-action messages, it must first use that operation's admission/validity fence, not infer action ownership from a cursor epoch.

## Minimal P03 consumer change

Add view-local `LOGE=null` and a log-initialized flag beside`LOGN`; reset both in`openJob`. Send the accepted`LOGE` on subsequent requests. Only an accepted `/log` snapshot advances the cursor/epoch: metadata is advisory, because reset/append can happen between metadata and log requests. Preserve `ownsView(id,gen)` and `current()` checks after **every** awaited body, single-flight cycle identity,15s body deadline, abort/backoff, hidden-page behavior and review/save ownership.

Validate new responses before modifying display: finite safe nonnegative integer indices with`base <= from <= len`, exact `lines.length == len-from`, string lines, bounded token, known reset enum, valid numeric counters. Retain the existing legacy response branch for valid old`{from,lines,len}` responses, including shrink→from0 refetch and authoritative empty responses; do not tighten the new interval invariant against the old backend's possible `from > len` shrink response. This keeps mixed-version fallback explicit rather than making malformed new-schema data look legacy. If any new-contract field is present, require the complete new cursor schema.

For an initial response or explicit stale/future/epoch reset, replace displayed messages with the response's last400 entries, set`LOGN=nl.len`, and accept its epoch. A reset must replace, not append a replay that duplicates old text. In an ordinary same-epoch interval require`from===LOGN`, append only that response, then advance. An unexpected epoch change must reset even if a malformed server failed to set reset; reject inconsistent flags/fields before publication. Keep user scroll-up behavior and stick-to-bottom for normal appends; test explicit resets separately. Put the fixed truncation/omission note in a dedicated status element, not into message sequence data or persistent diagnostics.

Existing incremental browser `textContent +=` can grow indefinitely and recopies displayed text, although initial display is limited to400. The recommended first PR bounds **backend producer retention** only and explicitly retains this existing incremental convention; it must not claim browser-memory bounds. If the controller wants bounded browser history too, that is a declared extra behavior choice: cap the displayed tail by entry/byte budgets while preserving initial400, with scroll tests. It is not necessary for the backend store contract and must not sneak in as a measured memory improvement.

## Limits and controller decisions

Count/UTF-8 bounds govern retained backend payload and entry count per job, not whole-process RSS. The caller already constructed its input string; existing exception fields, option notes, engine locals, subprocess captures and external references may retain original content independently. Python Unicode storage is not UTF-8 payload size; deque/tuple/string/int/lock overhead, allocator arenas and high-water reuse remain. Snapshots retain bounded string references until HTTP bodies finish; JSON escaping can multiply wire/output bytes and multiple concurrent responses multiply copies. The jobs registry itself is governed by existing job lifetime and can contain many jobs; per-job bounds are not a global job-count bound. Browser DOM history and desktop/updater/installer logs remain separately scoped.

No unresolved backend/client compatibility question remains if the controller accepts the specified epoch schema and minimal P03 adaptation. Implementation review must decide the final numerical defaults after actual calibration and whether to add a separately declared browser display cap. This research makes no measured sufficiency, latency, RSS, installed-platform or implementation-completion claim.
