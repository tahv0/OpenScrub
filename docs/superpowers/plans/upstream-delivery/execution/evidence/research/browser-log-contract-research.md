These are **proposed product defaults for supervisor disposition**, with costs and adequacy unmeasured:

| Independent browser bound | Default and accounting |
| --- | --- |
| Recent callback entries | 800 across the single active view; start/reset/reopen still selects at most last400. Count empty strings as entries. |
| Represented text | 2 MiB =2,097,152 bytes, defined as `2 * UTF-16 code units`, including the one LF between each pair of retained entries. This is an accounting ceiling, not JavaScript engine/DOM allocation size. |
| One represented entry | 8,192 UTF-16 code units, including any browser truncation suffix: at most16,384 accounting bytes. P12B's8KiB UTF-8 entry limit already fits this bound for valid Unicode. |
| DOM/state | At most800 entry spans,800 content text nodes and799 delimiter text nodes, plus fixed note/container nodes and O(800) bounded scalar/node bookkeeping. No hidden transcript, detached-node history, raw-string cache or growing observer queue. |

Initial400 remains compatible with **all** proposed P12B snapshots: the entire server snapshot is at most512KiB UTF-8; valid Unicode needs no more than twice that many UTF-16 accounting bytes, plus at most798 bytes for399 LFs. Thus even400 selected entries fit below2MiB. This arithmetic depends on actual P12B limits/normalization; it is not a measured distribution or a promise for an arbitrary old backend. Metadata still returns last30 independently. The800-entry choice gives room for subsequent updates; calibration may justify a different value only with an explicit disposition and revised initial400 proof.

One callback is one sequence entry even when it includes many newlines, CRLF, tabs, combining marks or emoji. Do not split physical lines into entries. UTF-8 payload bytes, JSON/wire bytes (escaping and framing), JavaScript UTF-16 units, engine string representation and DOM/layout allocations are different quantities. Count limits do not bound physical line count; the text limit bounds represented code units. Neither limit certifies renderer/process/whole-browser RSS or input JSON parsing cost.

## Smallest coherent display implementation

Choose **bounded entry spans in the existing pre-wrap div**, using the existing embedded vanilla JavaScript: no framework, dependency, worker or virtualized console. Each span has one content Text node and, except the last, a separate LF Text node. A bounded deque/array holds sequence number, node and accounted length; do not also retain entry strings. Strings returned in the current accepted body are temporary inputs only. Use `textContent`/`createTextNode`, never HTML interpolation. An empty entry still has an identity and produces its inter-entry blank line. Formatting must yield exactly `retainedEntries.join("\n")` with no trailing LF.

On append, add a separator node to the preceding last span and new spans for incoming entries. Evict oldest complete spans and their metadata before publishing a batch that would exceed either limit. Preselect the surviving suffix from cached lengths and incoming lengths; never mount the whole batch and trim afterward. The accepted body is already P12B-bounded. Account for bounded temporary fragment/new nodes and old nodes during publication separately; no implementation-owned attached retained state exceeds the limits. Eviction drops node references, listeners and any selected-range references. Mutation never rewrites the content Text node of a surviving entry.

A bounded string replacement is simpler to concatenate but recopies up to the entire capped transcript on each update, replaces every text node, invalidates selection, and needs an entry/offset model to restore reading position. It could bound retained text, but is a worse fit for the required surviving-entry anchor. Fixed multi-entry blocks reduce node count but require partial-block rebuilding and finer selection/anchor mapping; they save little with800 entries. Individual spans are the smallest option with stable entry identity. This adds real DOM bookkeeping/layout cost; accept only after measuring it, without assuming it outperforms one text node.

Keep a small view-local owner, for example `recentLog = {id,gen,element,entries,textBytes,displayBase,omitted,displayTruncated,anchor,positionNotice}`. Its operations are `replace(acceptedSnapshot, initialLimit=400)`, `append(acceptedSnapshot)`, `reflow()` and `dispose()`. Inputs have already passed P12B validation and fences. Rendering never writes `LOGN`/`LOGE`; the polling owner advances those from the authoritative accepted snapshot after synchronous successful publication. Guard any observer/frame callback against the same view and element identity. Disconnect/cancel on reopen/deletion; retain at most one pending frame and one saved anchor, not a scroll history.

## Response, omission and truncation rules

1. **Ordinary same-epoch append:** P12B requires the accepted interval to begin at `LOGN`. Entry `i` owns absolute sequence `from+i`. Display the newest suffix satisfying both browser limits, then advance server cursor to `len`, including accepted entries skipped or evicted locally. Trimming never changes the request cursor, invents received entries or triggers backfill.
2. **Initial/reopen:** after a fully accepted body, choose its last400 entries, then apply text/entry bounds. The proposed P12B body guarantees400 compatibility above. Reset local owner/flags/anchor; do not restore another view's old transcript or scroll. Initial empty history is still initialized; do not use `LOGN===0` as the sole initialization test.
3. **Stale/future/epoch reset:** replace with the accepted retained snapshot's last400; never append another epoch or a replay to old DOM. Empty authoritative replacement clears everything. Unexpected/inconsistent epoch/reset fields are handled by P12B validation before publication. No speculative clear API is introduced.
4. **Metadata versus body:** metadata `log_tail`, length, base, epoch or counters never change transcript, omission state or cursor. Accepted `/log` body is authoritative even if metadata was newer/older. Failed/malformed/obsolete bodies preserve valid display and existing polling recovery. Preserve P12B's explicit legacy-response branch; do not misclassify an incomplete new schema as legacy. With legacy unbounded bodies the local display can be capped, but initial400 for arbitrary huge entries and bounded transport/parse memory cannot be promised.
5. **Empty payload:** ordinary `lines=[]` with an unchanged valid absolute cursor is a no-op for text, scroll and selection; accepted counters may refresh the fixed note. An actual accepted empty reset replaces the display and cursor/epoch. Empty-string entries in a nonempty array consume sequences and count, even when invisible alone.
6. **Multiline/Unicode/oversize:** preserve ordinary strings verbatim. If a display input exceeds8,192 UTF-16 units, take only the bounded prefix needed to reserve `... [display entry truncated]`, backing off if the cutoff splits a valid surrogate pair. Do not encode or copy the full oversized input. Preserve one entry/sequence, record a display truncation flag and discard the original reference after the body finishes. Under compliant P12B this defensive branch is unnecessary; verify that backend truncation suffixes/content remain unchanged. Existing decoded body strings may already be large: this guard cannot bound a noncompliant server's network/JSON allocation.
7. **One note outside sequence:** add one fixed adjacent text element referenced by the scroll container's `aria-describedby`; use bounded fixed phrases for earlier omissions, producer/display truncation and lost reading position/history replacement. Derive producer facts only from accepted body counters/base; set local omission on initial suffix selection or browser eviction. Do not assume `base` equals evictions after a future explicit clear. Keep at most flags/scalars, replacing the note only when its text changes. No marker spans, repeated marker strings, extra cursor entries or diagnostics sink. Reopen/replacement resets local facts and derives them anew from the accepted interval; ordinary empty polls do not erase them.

## Exact proposed scroll and selection policy

Keep the existing40px bottom threshold, sampled **after all awaits/validation and immediately before mutation**: `scrollHeight - clientHeight - scrollTop <= 40`. Clamp against browser scroll range when restoring. Disable native scroll anchoring for this container (`overflow-anchor:none`) so it does not add another compensation to explicit restoration. Use immediate scrolling, not animation.

- **Ordinary append at bottom:** follow to the new bottom once per accepted batch. If no text changes, leave scroll unchanged. Mouse/touch/keyboard scrolling while the body is pending determines the final pre-mutation decision.
- **Scrolled up, retained anchor:** identify the first visible entry (use the span/delimiter geometry for blank entries), save its sequence and the pixel distance from that entry's top to the viewport top. After mutation restore that same entry and distance, clamped to its new height and valid scroll range. Do not compensate by total `scrollHeight` difference; wrapping makes that inaccurate. If rounding prevents an exact offset, tolerate at most2 CSSpx in calibrated tests.
- **Anchor evicted:** scroll to the top of the oldest remaining entry, set the single fixed lost-position notice, and stop. Do not silently jump to bottom or pretend the removed content is still available. Empty retained content means scrollTop0. The next actual user scroll refreshes the anchor/clears the position notice; a later genuine near-bottom state can follow normally.
- **Initial/new view and accepted stale/future/epoch replacement:** scroll to bottom of the new recent snapshot. Reset has no preserved reading identity; show a fixed history-replaced notice for noninitial resets. This deliberate policy change needs user-facing retention documentation and acceptance; it is not inherited P03 behavior. Do not move keyboard focus.
- **Resize/font/wrap changes:** retain only one latest anchor/bottom flag, refreshed on user scroll and successful mutation. A container ResizeObserver and font-loading completion hook coalesce into one view-owned frame, using that saved pre-reflow identity/offset to restore after width or font geometry changes; update the snapshot afterward. Container observation alone does not detect font changes inside its fixed height. This preserves the entry and a clamped pixel position, **not the exact same character** within a rewrapped multiline entry. Bottom readers remain at bottom. Resize alone does not select an older evicted anchor or create history. Verify observer-loop avoidance and cleanup. Zero-area/empty-entry geometry falls back deterministically to the next visible retained span or oldest retained entry.

Appending spans preserves surviving content nodes and native selection endpoints. LF delimiters are separate nodes so extending the tail need not rewrite selected content. If trimming removes a selection endpoint within this log, clear that in-log selection before detaching and use the omission/position note; do not retain detached nodes to preserve it. Replacement clears in-log selection. Never clear a selection owned elsewhere, take focus or copy text automatically. Verify browser copy across spans, blank entries and emoji; native selection/copy details remain browser gates. Keep ordinary keyboard scrolling possible with an accessible name and focusable scroll container. Do not use `role=log` or an aria-live transcript: repeated logs must not become an announcement flood. The adjacent fixed note can remain nonlive; existing P03 polling-error live status stays separate.
