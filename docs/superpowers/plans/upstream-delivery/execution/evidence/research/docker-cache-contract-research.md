## Minimal conditional implementation

**Candidate A, first to measure:** edit only `Dockerfile`, `Dockerfile.intel`, `Dockerfile.cuda` heavy dependency RUNs. Add the BuildKit syntax directive if needed and exactly one mount per heavy RUN:

```dockerfile
# syntax=docker/dockerfile:1
# CPU example; use openscrub-pip-intel / openscrub-pip-cuda respectively.
RUN --mount=type=cache,id=openscrub-pip-cpu,target=/root/.cache/pip,sharing=locked \
    pip install -r requirements.txt \
    ...
```

Remove `--no-cache-dir` only from pip commands inside that mounted RUN; preserve every filter, install/index argument, order, uninstall/restore operation, version and assertion. Intel/CUDA retain their existing initial `grep` as the first command. Use variant-separated IDs `openscrub-pip-cpu`, `openscrub-pip-intel`, `openscrub-pip-cuda`; pip must still distinguish platform/interpreter-compatible artifacts. Record CPU amd64/arm64 cache identity independently; add architecture suffixes only if isolation is chosen and actually exercised, declaring the required automatic build ARG in that stage. Sharing locked serializes competing use of the same ID; it does not establish cache persistence or artifact integrity. Confirm the actual image's pip cache configuration accepts this target rather than silently inheriting a cache-disabling setting.

Keep bootstrap, no-deps app install, final refresh and `docker/Dockerfile.opencv-cuda` unchanged for Candidate A. This isolates the claimed download-reuse benefit and retains the final refresh's `--no-cache-dir`. Do not add all donor mounts indiscriminately. In particular, existing layer reuse makes a bootstrap mount irrelevant to ordinary source-only rebuilds. A later app-install mount is justified only if captured build-backend downloads materially dominate the source case; preserve no-deps and final refresh if tested.

Expected supporting files, only after evidence warrants product changes: `tests/test_docker_build_cache.py` for contract regressions and concise `docs/DOCKER_BUILD_CACHE.md` explaining measured scope/lifetime. No workflow change is required for Candidate A. `.dockerignore` changes belong only to a separately demonstrated synthetic-context requirement. All required COPY inputs must remain available, including B02b's namespace and notices/icon. No standalone training ignore fixture authorizes training installation or bundling.

**Candidate B, optional source-only optimization:** move the same refresh ARG/RUN as a single block immediately after model prefetch and before every app COPY/install. This allows local app-only edits with an unchanged ARG to reuse refresh work. It still rebuilds the app tail whenever refresh changes. In CI every run already receives a new run ID, so relocation cannot remove the explicitly requested refresh; it can additionally invalidate an otherwise reusable app install on refresh-only runs. Measure that cost too. If ever adopted, touch the three app Dockerfiles, their refresh comments, the corresponding workflow comments (current `docker-image.yml:25–28`) and tests/docs; retain workflow executable behavior.

Do **not** move refresh before heavy dependencies, model prefetch, CUDA source compilation/copy or provider installation to chase reuse. The current late apt upgrades patch runtime OS packages after those native dependencies are laid down; moving refresh before a later native artifact copy/install could reintroduce older vulnerable files or change link/runtime conditions. Even before-app relocation is conditional: source metadata uses Hatchling with `--no-deps`, but isolated backend build/download occurs afterward and its final contents must be checked. Keep both OS dist-upgrades and pip/setuptools/wheel upgrades, apt-list removal and the final patched package inventory/security effect equivalent. Cached heavy Python dependencies and compiled base artifacts are not comprehensively security-updated by the weekly OS/bootstrap refresh today; do not broaden or silently weaken that established policy.

Default decision: preserve final placement. Do not adopt A or B if actual relevant builds show no material benefit, unreliable reuse, a cache/disk cost outweighing saved work, or changed runtime/security behavior. A focused no-adoption disposition with measurements satisfies P13 better than mandatory production churn. Source-only inspection supplies no numeric improvement or threshold; agree and record the target workload and materiality criterion before timing.
