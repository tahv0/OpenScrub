# P07b manual-addition replay contract research

**Finding:** A local orange manual draft cannot itself be selected or edited. A **committed but unacknowledged** addition can nevertheless be edited: the live editor's ordinary scrub GET can load its new indexed server row before the save POST resolves. Existing move/resize, time, and Remove blur controls then create newer indexed edits while the original addition draft stays unchanged. P07b can preserve that behavior without a new editing workflow.

**Required contract precision:** compare an ID replay with immutable **creation** data, never with the detection's current geometry, time bounds, or enabled flag. An ID plus a comparison against mutable detection fields would conflict with this real flow. No supervisor ruling or new UI design is needed; the P07 card's “identical geometry” wording needs this interpretation before implementation.

## Bounded actual-function check

`probe.py` reuses the pinned P07a Node VM harness and exact evaluated `APP_JS`. It extends only DOM primitives to dispatch the real `beHook` pointer listeners. Exact AST bodies of `job_save_edits`, `job_boxes_at`, and `job_detections` run with a task-owned synthetic JSON report and the actual atomic writer. Their resulting server row is supplied to the deferred scrub response. No save/editor logic is replaced. This is a deterministic function/interaction check, **not** a real browser or HTTP test and not a transaction/restart test.

Both acknowledgement-success and acknowledgement-loss scenarios perform this sequence:

1. Actual Add box clicks create screen box `[20,20,60,60]`, times `[0,4]`, reference time `1`. Attempting to select/drag the unpublished orange draft creates no edit.
2. Save snapshots that creation. The actual server body commits it as row `i=1`; the POST response is held.
3. Actual `beScrub` fetches the committed row. Actual pointer selection/move/corner resize produces content box `[30,30,80,90]`; Apply times produces `[0.5,5]`; Remove blur produces `enabled[1]=false`. The original `BE.adds[0]` is still byte-for-byte equal to its creation snapshot.
4. Successful acknowledgement removes the original addition only. The three newer indexed edits remain pending, and no render starts. The next save contains those edits and **no** manual addition.
5. Lost acknowledgement retains the original addition and those indexed edits; no render starts. The next save contains the **original** manual creation and the newer indexed patches together. The probe captures this payload and rejects that research retry before commit, avoiding repetition of the known append-duplicate baseline.

Applying only those captured indexed patches with the actual server function changes the live row to the newer box/time/disabled state. Comparing the original replay to that live row fails. With the existing route's order (indexed patches before manual append), a proposed mutable-row equality check could fail on the very first replay carrying newer edits. Moving the equality check earlier only postpones the problem: after a committed edit or a second lost acknowledgement, the row already differs. Replaying creation must neither reject this legitimate retry nor overwrite/re-enable the edited row.

The existing `write_report` raw `source_report` publication path (`openscrub.py:6305–6320`) was also executed with seeded **proposed** ID/creation fields on the disabled, edited fixture row. All rows and additive fields survived actual file publication and a fresh JSON read. This verifies the existing preservation mechanism, not implementation of IDs or an end-to-end render/server restart. `_decode_report` (`6356–6377`) builds a rendering subset; ID preservation should continue through the raw review document, without adding inference labels or depending on `Detection` serialization.

## Proposed smallest contract: what, why, when

**What — identity and replay equivalence.** Scope opaque `manual_id` values to the job's logical review report. The same string in another job is independent. Generate a fresh ID once when a real ordinary addition is completed, retain it on that draft across saves/failures/job revisits, and include it in the existing `manual` payload mapping. Never generate it for every Save or deduplicate by coordinates. Distinct IDs with equal creation fields remain distinct additions; repeat occurrences of one ID in a request follow the same equivalence/conflict rule.

Persist `manual_id` and a compact immutable creation record on the appended detection, in the same report publication. Suggested name/shape (proposed, not present today):

```json
{"manual_id":"opaque-id","manual_creation":{"t_start":0.0,"t_end":4.0,"cbox":[20,20,60,60],"aoff":[0,0]}}
```

Define equivalence by the effective creation fields the existing endpoint actually produces: normalized numeric `t_start`, `t_end`, integer content-space `cbox`, and reference offset `aoff`. Apply the existing default `t_ref=t_start`, frame selection from `fps/cum`, and integer coordinate conversion **before** comparison. `t_ref` matters through its selected offset; two raw reference times or fractional screen boxes that create the same effective row are equivalent under this proposed effective-field policy. Include `aoff`: reference offsets are retained in detections and used by rendering. Fixed `category=manual`, `text=user-drawn`, confidence, initial enabled, and initial `last_seen` are server-derived constants/defaults, not caller-controlled creation fields. Incoming category is currently ignored. Do not compare current `enabled`, mutable current box/times, or derived/clamped `last_seen`.

An existing matching ID+creation record means “creation already happened”: do not append and do not reset any live detection fields. Different effective creation fields under that ID are an explicit conflict. Neither changing an ID to bypass the error nor converting a user's later edit into a second addition is acceptable. Retaining the immutable record is necessary because the real indexed UI edits the same live fields an ID-only current-row comparison would read. A hash of canonical normalized creation fields could represent the same invariant, but the small explicit record avoids introducing a hash/canonicalization format.

**What — later edits and acknowledgement.** Preserve P07a's separate creation versus indexed desired-state bookkeeping. No new client creation snapshot is required for the verified flow: `BE.adds` already retains original creation data, and `BE.ov`, `BE.times`, and `EDITS.enabled` retain newer desired values. Keep identity-and-value cleanup; do not acknowledge all equal-geometry additions. Preserve IDs through the editor-add serialization, which currently copies only `t0/t1/tref/box` into API field names. `MAN` has no production creation control to redesign; if retained as a supported internal container, identified drafts must receive/reuse IDs once rather than at each retry.

No new response→row mapping is required for this existing UI flow. A row becomes editable only through a GET that already supplies its `i`. Existing `ok:true` means the submitted creations were acknowledged; P07a can remove their unchanged drafts while keeping newer indexed patches. On lost acknowledgement, retransmit the original creation with the same ID plus the pending indexed patches. The server checks creation identity independently and applies those patches normally in its transaction. Never infer that request failure cancelled a commit. If future product work adds editing of an unmaterialized local draft, it must supply immutable submitted creation plus desired values and an ID→row acknowledgement/lookup before routing those edits; that workflow is absent here and should not be implemented for P07b.

**Why — durable local replay without a revision system.** Store the ID+creation record in the authoritative report so an actual process restart/new request can rebuild its lookup by reading that report. Ordinary indexed edits, Keep choices, and rendering must preserve the metadata and row identity. The pinned raw-document publisher already preserves unknown fields. Browser drafts are page-memory only today: a reload loses unsaved local additions/newer edits, so do not claim durable client retry/recovery. A saved replay request retaining its ID must still deduplicate after server restart/report reload. Existing GET need not expose IDs merely to add deduplication; exposing them would be additive only if needed for a specifically supported reconciliation flow.

**When — after the transaction foundation.** Implement under P06B's final reviewed read/apply/publish boundary, independently of the moving Task622 code. Validate incoming identified creations and detect conflicts before publishing any changes; a conflict must leave the whole request unapplied. Lookup, indexed patches, replay checks, distinct new additions, and publication must use the same authoritative report transaction. No journal, general revision system, or external identity store is required.

**Legacy behavior.** No-ID requests retain the current append behavior, including equal-coordinate additions. Existing rows without IDs are not retroactively matched by geometry or assigned guessed creation identities. Preserve unknown/additive data on those rows. An imported row with an ID but no trustworthy creation record cannot safely have that record reconstructed from its mutable current geometry; choose explicit error/migration handling before accepting its replay.

## Open decisions and implementation acceptance evidence

No P07a/P07b behavior contradiction remains if the immutable-creation distinction is adopted. Decisions still needed at implementation are the metadata field/version names, ID format/length validation, conflict error payload/status (409 is a reasonable proposal), and handling imported identified rows lacking a creation record. Confirm the effective-field equivalence policy above; literal `t_ref`/screen-box identity would be a stricter alternative and must be documented/tested if chosen. A replacement scan/report is a new logical creation scope; stale requests across that boundary depend on the report/admission contract and are not resolved by addition IDs alone.

P07b acceptance should cover the verified delayed-ACK indexed-edit flow for both success and loss, including a retry whose own acknowledgement is lost after newer patches commit; immutable creation comparison after later box/time/Keep changes; equal-geometry distinct IDs; incompatible ID reuse and atomic rejection; omitted `t_ref`/normalization; legacy no-ID append; metadata/row-order preservation through real render, restart/reload, and retries. Retain P07a job/view ownership and pending-edit cases. These are proposed implementation checks, not passing P07b tests from this research.
