## Proposed additive v1 record

Use a fresh field name, for example **`manual_plate_quad`**, so old experimental `plate_quad` arrays cannot be silently interpreted as the new source-bound contract. Append one optional dataclass field after `poly`, default absent/`None`; preserve Python 3.9 syntax and all twelve existing positional arguments. Raw JSON stores one record per existing plate row:

```json
{
  "manual_plate_quad": {
    "version": 1,
    "points": [[0.10,0.20],[0.25,0.18],[0.26,0.30],[0.11,0.32]],
    "source": {"input_sha256":"<existing scan-source digest>","stream_index":0,"width":640,"height":360},
    "frame": {"index":5,"pts":5,"time_base_num":1,"time_base_den":24,"time_seconds":0.20833333333333334}
  }
}
```

The example describes a 24fps CFR source. `pts` and time base are actual decoder/resolver metadata, not values manufactured from a requested slider time. Index is zero-based in the **inspected scan source**; display time is derived from PTS/time base. If a supported decoder has no independently justified PTS, P10A must define its bounded exact-index alternative explicitly; P17 must not invent plausible PTS. The stored `source` describes actual decoded dimensions/stream, never browser client dimensions, crop dimensions, detector box, output dimensions or a basename. A declared single supported stream may use index 0 only when the decoder selection agrees.

**Geometry convention:** continuous full-source-frame **edge** coordinates, origin top-left, positive right/down, `(u,v)=(x/W,y/H)`. `[0,1]` includes the outer image edges at `W/H`; conversion back is `x=u*W,y=v*H`. This deliberately differs from cbox-relative `poly` and from pixel-center `x/(W-1)`. Four distinct finite numeric pairs, excluding booleans and strings, must form a simple strictly convex ring in clockwise screen order (positive shoelace area with y down). Require consistent nonzero edge cross products, positive area and a nondegenerate raster; reject concave, self-crossing, repeated or collinear points. UI shows numbered corners; cyclic rotation can be canonicalized by smallest `(y,x)` first without sorting a bad ring into a good one. Preserve sufficient precision and revalidate after any serialization rounding. Do not reuse the donor's arbitrary 8-pixel minimum without an explicit product choice.

**Clipping:** accept points on source edges; reject out-of-frame writes rather than silently clamping them into another polygon. For a plate cut off by the image, the user specifies its visible four-corner region within the frame. Compute the raster ROI from the quad's own pixel bounds plus the **existing configured pad and applicable drift**, then floor minima/ceil maxima, intersect with `[0,W)×[0,H)`, translate to ROI coordinates and rasterize under one documented rounding rule (the existing nearest-integer silhouette rule is the smallest compatible choice). Clip the resulting mask to the frame. Never crop the quad to the detector's cbox. Check finite derived bounds/int32 safety before native conversion. Fully outside imported or degenerate geometry cannot become a successful empty mask.

For a first release, invalid/unsupported imported v1 geometry is retained in raw JSON but is ineligible for tightening and uses existing valid detection coverage with a visible explanation. Invalid writes fail before any report publication. Missing/invalid fallback boxes remain the separate P16C-G error contract; a quad is not permission to invent coverage for a malformed detection. New quad precedence over existing `poly` is limited to category `plate` and the verified bound frame; other frames retain their exact existing geometry behavior.

**Padding decision:** preserve the current `pad+drift` setting for the quad's outward dilation, including explicit per-category fill modes; initialize only from an existing plate row. The donor's hard-coded one-pixel dilation and two-pixel ROI are not adopted defaults. User-authored corners can still tighten the shape around the whole plate. Editor preview must show the effective padded mask separately from corner handles; the corner line alone is not render coverage.

### Exact temporal eligibility and bounded identity owner

The entire `t_start/t_end`, `last_seen`, `cbox`, `aoff`, enabled choice and group membership remain intact when saving a quad. A quad changes geometry on **one inspected input frame**. Keep existing dense deduplication; an editor row/group representative must resolve to the concrete raw row at that frame. Do not copy a quad onto whichever sibling wins deduplication. It is neither an exact-frame replacement detection nor a reason to shorten the report interval. On any other render index, changed source, unverified decode, missing identity, unsupported transform or unresolved normalization relation, use existing full-plate coverage. No nearest-time matching, multiplying the same corners through moving boxes, track-wide writes or automatic perspective claim. Duplicated normalized frames remain different indexed samples unless a separate mapping explicitly certifies them; equal pixels alone do not grant propagation. O01/O02 may later define conservative gaps/tracking policies, with no P17 default change.

The missing owner is **P10A's exact editable sample resolver**, consumed by both image and geometry. Minimum transient response: opaque sample/source-generation token, requested time, actual source identity/dimensions/stream, actual frame index and PTS/time base, actual time, exactness/fallback status, and crop origin if cropped. GET image and geometry must refer to that same sample token; stale image/geometry/POST conflicts fail with editing disabled. An exactness token must come from the resolver's verified decoder policy, not `cap.set()` success or a guessed counter. The admitted file lifetime/source generation must remain owned while sampling and validating a save.

For persistence, reuse the **already computed scan input SHA-256** where available; do not hash a full video at every edit or introduce implicit hashing of originals/HDR sources. P10A can add a bounded server generation token plus file stat fingerprint for in-flight invalidation, but path/stat/UUID alone does not provide durable byte equivalence. On reopen/render, the existing pipeline scan hash plus matching actual source/frame metadata can revalidate the record. Missing digest/exact frame information disables tightening until an explicit supported verification path exists. External replacement during decode/render remains a source-owner race requiring stated limits or stronger ownership; this research does not establish immunity to it.

For SDR rendering of that identical scan source, use the record only at its exact index after identity validation. For HDR/original rendering, the normalization/source-selection owner must supply an explicit identity spatial transform and exact scan-frame → render-frame relation, with actual destination identity/dimensions/index/PTS. A different size, crop, rotation, stream or resampling is **unsupported in v1** unless explicitly mapped and tested. Absent that proof, HDR retains full-plate fallback and the UI reports that the saved quad is unavailable for this output source. A fixture with an injected declared mapping alone does not prove the normalizer supplies one. No new general transform framework is needed; support the existing verified identity relation or decline tightening.
