# P03 polling ownership and bounded requests — pinned baseline

Status: read-only baseline complete. Product source/runtime came from the full Git export of reviewed P07a `92124753736e287ac800af91f0ac96f3e96c01be`, never the moving native worktree. No product changes, commits, models, installations, user data, full suites, builds or nested agents. Plan context was limited to P03 and R03; those planning documents are not present in the pin. Donor `08f432b6` was inspected only for polling/helper provenance, without importing its code or unrelated features.

The minimal P03 delta is a cycle owner bound to **existing `(CUR, VIEW_GEN)`**, a deadline spanning fetch and JSON body consumption, status/error handling, and bounded recovery. P07a already prevents cross-view metadata/log/review/audio publication. Preserve those existing fences and per-job draft ownership. The demonstrated defects are same-view overlap, pending-body ownership and failure feedback, plus one poll-initiated downstream review publication case.

## Actual call/publication trace at the pin

Source positions below refer to pinned `openscrub_web.py`, reproduced in `source-excerpts.txt`.

- `openJob` (2150–2171) pauses the previous editor video, removes fetched editor display caches, runs `trimReviewDraft`, increments `VIEW_GEN` **on every open including same ID**, selects/reuses `REVIEW_DRAFTS[id]`, resets progress/log/shell state, clears the old interval, starts `setInterval(refresh,900)` and immediately calls `refresh`. There is no request cancellation or in-flight owner. Preserve its draft snapshot/cleanup and status behavior.
- `delJob` (2138–2148) awaits DELETE and checks status; after success deletes that job's draft and, when still current, increments generation, clears current owner and interval, and empties detail. Pending fetches are not aborted. Its view reset is already sufficient to suppress a successful late response.
- `refresh` (2186–2272) captures `id=CUR, gen=VIEW_GEN`, then awaits fetch **and `.json()`** for metadata. Neither HTTP status nor deadline is checked. After the await, `ownsView` gates shell insertion, preview event setup, phase/history, ETA and progress. No await intervenes among those publications.
- It captures current log DOM element and scroll stickiness, then awaits fetch **and `.json()`** of `api/jobs/${id}/log?from=${LOGN}`. Afterward another `ownsView` gates log DOM/cursor, image src, warnings, action shell/phase and downstream setup. Those synchronous actions still belong to the captured view; mutable `CUR` in preview/download URLs does not introduce another asynchronous gap there. Overlapping cycles in the *same* view pass both checks.
- Log route (1066–1071): `from=max(0,int(query))`; returns `{from, lines:job.log[from:], len:len(job.log)}`. Client ignores returned `from`. Initial backlog >400 slices the last 400, then sets `LOGN=len` when any lines were appended. Otherwise cursor remains unchanged, including zero-line/shrunk-server responses. Concurrent `from=0` responses each append identical lines. Scroll position stays pinned only when previously near bottom.
- After logs, scanning preview sets an image URL with current timestamp and DOM onload/onerror show/hide callbacks. These callbacks operate on their captured image element; switching removes it. No new P03 image-generation owner is justified. Live-preview byte publication and P09 thumbnail scheduling are separate work.
- `refresh` invokes `loadReview()` only on phase transition into review, without awaiting its returned promise, and finally invokes independent `loadJobs()`, also without awaiting. Therefore polling-cycle completion does not mean downstream review setup completed. Network/JSON failures reject `refresh` without catch; the interval keeps firing. Failure to parse logs also prevents later action/preview/warning work in that particular cycle.
- `loadReview` (2777–2863; the pin has no `buildReview` function) captures `(id,gen)`, calls existing `showPanel('review')`, awaits detections, checks `ownsView`, then synchronously publishes `DUR`, display enable values (overlaying `EDITS.enabled`), grouped review HTML, thumbnail URLs, marquee hooks and save status. It cannot cross views, but it can publish after a newer phase in the **same** view. Automatic polling initiation needs phase/cycle eligibility; preserve deliberate done-phase “Re-open review” calls and pending choices.
- Preview/editor is user-initiated through the existing review button, not automatically fetched by `refresh`: `loadBoxEdit` (2275–2336) captures `(id,gen,editor)`, awaits mediainfo and fences publication, installs image/video callbacks with identity checks, then awaits `tlInit`. `tlInit` (2405–2434) awaits report headers and JSON, checks `ownsView` and `BE===editor`, then publishes timelines, merges loaded stored audio with any local audio choices, sets saved baseline/loaded state and renders transcript/suggestions. Catch also fences its timeline fallback. After this await `loadBoxEdit` rechecks identity before `beScrub`; boxes response is independently fenced. The controlled late report after switching did not mutate B. P03 does not require another audio generation or broad async/editor rewrite.
- There is no polling `visibilitychange`, focus, pageshow or online handler in this pin. Only other unrelated intervals exist (job list 5 s, model/download/tracking/update/extras flows). No save, render, download, manual tracking or global job-list deadline change is established by this research.

## Minimal future owner/helper contract

1. Reuse `VIEW_GEN` and `ownsView(id,gen)` as the view identity. Add at most one local polling-cycle object/slot containing captured `id`, `gen`, controller, promise and retry state; use **object identity** to prevent an old `finally` from clearing a newer owner or scheduling its timer. Do not introduce donor `JOBVIEW` or another global generation. Draft state remains owned by existing `REVIEW_DRAFTS`/`EDITS`.
2. One admitted metadata→log cycle per active view. A pending invocation returns/coalesces onto its owner's promise or is ignored. Use one owned timer; switch, same-job reopen, successful delete and intentional stop clear the timer, invalidate the cycle owner and request abort, then allow the new view immediately. Late obsolete results cannot publish or control the new retry/timer. Keep every existing job/view fence.
3. Use a helper local to this UI for polling metadata/log only. Its proposed 15,000 ms request deadline must cover fetch headers, status/error-body handling and final JSON consumption. Race the *whole operation* against deadline/cancellation, abort the fetch controller on stop, and remove timer/listener state in `finally`. Check `response.ok`; catch transport/parse/status/timeout failures as controlled polling failures. An abort by itself does not guarantee settlement when a body/transport ignores it: a separately rejecting race releases the **logical caller/cycle slot**. It cannot force an uncooperative underlying transport/server to terminate; late losing promises must have rejection handlers and no DOM side effects. Actual browser requests normally honor abort, while ignore-abort behavior needs synthetic helper tests.
4. After a successful cycle retain the existing nominal 900 ms healthy cadence in all current phases; do not import donor idle 5 s cadence. A timer chained after completion avoids overlap but means slow requests add their duration to the interval; state that scheduling semantics explicitly if chosen. Failure retry can use 900/1800/3600/7200/10000 ms (or a comparably simple documented sequence), capped at 10 s and reset on success/new view. No scan retry/render action is part of polling recovery. The numbers 15 s and 10 s are reasonable initial UI bounds/proposals, not tuned measurements: synthetic gates established the missing bound, not an empirically optimal threshold.
5. Treat server cursor metadata as authoritative even when no lines arrive. Reconcile a smaller `len` and reset/clear stale log DOM as appropriate, then fetch from the reset position to recover current lines (the existing server returns none when old `from > len`). Honor the current route's `{from,lines,len}`; adding donor `limit=400` or a new log API is unnecessary. Preserve last-400 initial display and scroll behavior.
6. Scope automatic downstream review publication separately from intentional manual reopening. A poll-initiated `loadReview` should be allowed to insert only while its captured job/view is still current and the current phase still permits that automatic review. If passing a polling owner/callback, it must represent ongoing eligibility, not reject every slow detection merely because the next **same-phase** cycle began; otherwise review can disappear without retry because phase-change triggering will not fire again. Do not turn a pending review/audio fetch into an unbounded metadata/log cycle, silently apply polling deadlines to report saves, or replace P07a audio/draft owners. A phase eligibility gate for this automatic path is enough to target the observed done-phase insertion while keeping manual “Re-open review”.
7. For hidden/resume behavior, one existing-view owner remains the authority. A hidden stop and idempotent visible/focus/pageshow/online wake may cancel old work and schedule one immediate fresh cycle. Browser/native suspension can freeze JavaScript deadline/retry timers too; a 15 s timer is not a hard wall-clock guarantee while suspended. On resume invalidate obsolete work before publishing and coalesce multiple wake events. Real browser/OS suspension remains a manual/platform acceptance check; CDP freeze plus fake visibility is only controlled lifecycle evidence.

Donor provenance: its polling single-flight/controller identity and whole-request Promise race illustrate applicable ideas. Its additional `JOBVIEW`, 30 s backoff cap, idle 5 s cadence, log route limit, learned/video sections, thumbnails and broad `reviewRequest` reuse are not this contract and should not be imported wholesale.

## Concrete future acceptance matrix and boundaries

| Acceptance control | Required observation |
|---|---|
| Existing A→B, A→B→A, same-ID reopen, delete late metadata/log/body | Preserve P07a view fences; old cycle cannot write new DOM, clear new slot or leave a retry timer. New view starts immediately. |
| Repeated original timer/manual/wake callbacks while headers or body pending | Exactly one admitted logical cycle per active view; no duplicate metadata/log growth and no repeated log lines. |
| Fake clock just before/at/after 15 s while fetch hangs or body ignores abort | Entire helper rejects/releases by simulated deadline; controller abort requested; stale fulfillment/rejection later cannot publish or affect new owner. No real 15 s wait per case required. |
| Transient transport, malformed JSON, HTTP error, timeout → success | Controlled failure feedback; no unhandled rejection; bounded retry ≤10 s; next success restores polling and resets retry. No rescan/render POST. |
| Cursor advances, empty response, initial >400 rows, server length reset | Authoritative cursor reconciled; no duplication or permanent `from` beyond server end; intended initial trimming/scroll retained. |
| Slow automatic detections across same-view phase change | No review inserted after newer incompatible phase; manual done-phase Re-open review still works; slow same-phase detections remain eligible. |
| Pending editor/audio setup → new view/reopen | Existing editor/view fences and local audio/draft merges remain intact; no competing owner or draft cleanup regression. |
| Hidden→visible/focus/pageshow/online bursts and platform resume | At most one owner/timer and immediate usable recovery when runnable; explicitly separate fake visibility/CDP tests from native timing coverage. |
| Existing help, preview, edit/save overlap controls | Austin help/preview interactions, save snapshot/ack fencing, newer choices and inactive draft cleanup remain unchanged. |

Scope ends at polling metadata/log ownership and the concrete automatic downstream review publication gate. Saves/downloads/scans/render POSTs retain their own semantics, independent global job-list scheduling is not reworked, P09 scheduling and the completed save/thumbnail research are not repeated. This report is baseline evidence and a proposed acceptance contract, not a fix or a passing future implementation.
