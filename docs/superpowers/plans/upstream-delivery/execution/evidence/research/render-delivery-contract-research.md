Status: proposed contracts for root review; not implementation approval. Date: 2026-11-17.

None alone closes P16C, and none supplies crash-atomic pair publication.

The scalar rule should preserve Python int/float, bool's existing numeric arithmetic, standard real numeric scalar types that already work in the formulas (including Fraction), and NumPy real integer/floating scalars. Keep original numeric values and the existing arithmetic/rounding, rather than converting all boxes to float or int. Use scalar-aware finiteness without narrowing an extended real/large integer to binary64 merely to validate it. Reject complex/string/object-array scalars, nested box shapes, mappings and unsized iterators that the renderer cannot currently index safely. Preserve list/tuple and one-dimensional NumPy/indexable array containers; do not require `list` or `tuple`, use a whole-array truth test, `np.asarray` all geometry, or copy each trajectory. Decimal/custom objects that fail the renderer's existing mixed float arithmetic are not a new promised coercion surface. A boundary test must establish any additional scalar/container support claimed by implementation.

Proposed small engine-local helpers: a finite-real scalar check, fixed-width numeric sequence check and `_validate_render_geometry(detections,cum,bands,fps,pad,band_margin,...)`. Helpers inspect existing values, return no replacement document, and allocate only small per-box tuples when needed. Preflight traverses detections plus trajectory/band entries once: O(D+C+B) time, O(1) extra space apart from diagnostic context; it does not expand each detection across every frame. Do not add another smoothing/coverage pass or change the existing coverage algorithm's complexity.

Run source preflight at the start of `run_render`, before `apply_coverage` and before optional clip duration probe; validate transformed coverage boxes immediately afterward. Also preflight at entry to both direct renderers before `VideoCapture`, encoder availability probes, callback logs that may trigger acquisitions, or `Popen`. Duplicate scalar traversal at those public boundaries is acceptable for direct-call safety; a validated-state cache or public bypass flag is not justified.

### Derived values and painting

For each actual frame, validate the selected `(ox,oy)/(bx,by)`, source cbox/aoff used, translated unpadded box, drift intermediates, px and padded endpoints **before** clipping/int conversion. Finite source inputs can overflow in subtraction, addition or extent arithmetic. `apply_coverage` also needs checks of union expansion endpoints before its `int` calls at 3792–3793, rather than only validating already converted results. Use a shared tiny calculation/validation helper in SDR and HDR if it prevents those two formulas diverging; do not extract an engine pipeline.

Positive source extents are distinct from painting intersections. A positive finite source box entirely outside the frame is legal and stays a no-op. A very small positive box may become empty after existing integer conversion; retain that no-op. Finite negative pad can make the requested derived ROI empty; retain its existing no-op semantics. Validate original source extents and unpadded translated extents before padding/clipping, so neither can conceal zero/reversed/nonfinite source geometry. Bands with finite empty intersections are also no-ops. Do not turn legal emptiness into an error by applying the source-positive test indiscriminately to the already clipped ROI.

Direct painting callers still bypass render preflight: `blur_region`:3115, `blur_silhouette`:3179, `_blur_yuv10`:3618, `_blur_silhouette_yuv10`:3682. Check finite endpoint values before their `int` conversions, preserve finite empty region no-ops, and require a valid finite positive unpadded `poly_box` when silhouette geometry uses it. Preview's rectangle/int path at 4222–4235 and safety-band preview at 4252–4254 also need derived finite guards; fixing only blur functions misses preview. Polygons themselves, int32 conversion/fallback and normalized point errors remain P16B. A valid known cbox permits that card's fallback; an invalid cbox never authorizes a full-frame mask or successful unredacted render.

Raise one clear `ValueError` family with stage, render-subset ordinal (or enabled raw row ordinal at decode), field, and frame index/time where known: e.g. `invalid render geometry: detection 3, frame 6, translated cbox must be finite`. Never interpolate `d`, `d.text`, category/custom text, raw values, whole report or source paths. Do not stringify the caught conversion exception if it can contain raw input. No stable raw-row-index field is required; preserve existing model/constructor positional compatibility. Numeric time/frame identifiers are sufficient diagnostics.

## P: small transient delivery and shared report staging

### Minimal interfaces and compatible callers

Proposed engine shape:

1. Extract each renderer's current computation body into a private `_render_into` / `_render_hdr_into`, retaining R's ownership scope. Public `render`/`render_hdr` keep their existing signatures and return behavior, reserve a private sibling output, call the private body, then replace final video once on success. `run_render` uses the **same private body** with an outer delivery stage and commits only after its report is ready. Two real consumers justify these behavior-preserving extractions; duplicating the renderer or recursively staging twice is unnecessary. Direct callers still receive geometry preflight in the private entry/body.
2. Extract report **construction** from `write_report`:6286–6343 into one private `_report_document` with optional `output_bytes_path`. `output_path` still names the final path; only hashing reads staged bytes. `write_report(path,args,state,output_path=None,publisher=None)` remains compatible and delegates to construction plus its existing publisher/default. No document deep copy beyond current retained-document merge and no source-report mutation.
3. In `openscrub_internal.reports`, extract a private context/function for restrictive same-directory stage/serialize/flush/fsync/close from `atomic_report`:19–31. `atomic_report` and paired render delivery share that exact implementation. If Task632 adopts a serializer, its reviewed implementation is the **single** encoding owner; no second `json.dump`, copied encoder loop or render-specific buffering. This is the only prepublication report-stage extraction required. No separate prerequisite PR is necessary unless root wants to review that behavior-preserving extraction first.
4. Add only an optional render-specific callback such as `cb.publish_render(delivery, summary)`. `delivery` is a short-lived internal value owning staged/final paths, prepared rollback artifacts and pair commit/cleanup; `summary` is detached data for web success. It must not serialize handles, operation identities or temporary paths. Default CLI/GUI uses the same delivery commit without web locks. Web installs the callback to validate the captured owner/Event and commit pair plus output/done/progress/eta under the stable report lock.

Scan-only calls and direct `write_report(...,publisher=...)` retain `(path,doc)` and current semantics. Render callbacks with only the existing `publish_report` must still be invoked with the final report path and full document; do not silently bypass them or add required positional arguments. A compatibility adapter can treat that legacy callback as the second publication action after installing staged video and restore owned finals if it raises. Its arbitrary non-file side effects are outside rollback. When it returns without publishing, retain that caller's historical behavior rather than inventing a requirement to inspect/rewrite its report. The new web path uses `publish_render`, never recursively calls `publish_report` while already holding the same nonreentrant report lock. A fully staged default/new-hook report path is required; a legacy callback still owns its own publication implementation and cannot be promised to use the extracted stage serializer. Tests must cover these distinctions explicitly.

All encoding, report construction, stage serialization/fsync, output SHA and any large backup copy occur outside report/JOBS/VAULT locks, while the operation/lifetime remains active. Hash `delivery.video_stage`, record final absolute `dst` in `provenance.output`, and retain exact current input hash/source pin/settings/raw row/unknown/audio merge behavior. Temporary stage names never appear in successful result, report provenance or `job.output`. Reject aliased/colliding source/output/report destinations before staging rather than attempting to roll a source into a report; no broad path-policy change is needed.

### Stage naming and cleanup

Reserve exclusively with restrictive permissions in the destination directory, close reservation descriptors before encoder open/replace, and preserve the final **container suffix** for FFmpeg and hvc1/audio selection (3940–3944/4110–4131). A `.tmp` terminal suffix would change format inference. Proposed discardable video name: `.render-<random>.tmp.mp4` (or `.mov/.mkv`); no-extension/other supported direct destination must retain its actual muxer behavior through an explicit equivalent muxer choice rather than assuming MP4. OpenCV fallback's `.noaudio.mp4` is another owned stage, not a final path. Its successful replacement targets the outer video stage.

Current vault `encrypt_tree`/`decrypt_tree`:164–190 unconditionally deletes names ending `.tmp`; `tree_locked_state`:194–204 ignores them. Therefore `.render-*.tmp.<container>` is not presently recognized as discardable, while necessary recovery ending `.tmp` would be deleted. Propose a narrow reserved-name predicate shared by those three vault consumers: current terminal `.tmp` **or** the exact exclusively generated discardable render-stage pattern (including its fallback intermediate). No broad hidden-file deletion. Keep report stages on existing `.report-*.tmp` convention. Reserve different rollback names, e.g. `.render-recovery-<random>.video` and `.render-recovery-<random>.report`, which are normal sensitive files for vault encryption, not discardable leftovers. Successful commit/rollback removes recovery artifacts; failed rollback retains them. They are not a persistent generation archive.

Recovery evidence must include which finals previously existed, stage/backup roles and which replacement/restoration failed. Prepare a tiny private task-local descriptor, e.g. `.render-recovery-<random>.json`, with original presence flags and backup/final roles **before commit, outside locks**; normally remove it with the other transient artifacts and retain it on failed rollback. This avoids depending on a fresh descriptor write after the filesystem has already refused restoration. The in-memory error carries the exact failed steps; if a safe descriptor update also fails, the original prepared roles remain sufficient to identify recovery artifacts. This is not a journal/database or automatic crash-recovery claim. A leftover descriptor is conservatively recovery-required on rehydration; its mere existence does not prove a particular crash point or a corrupt pair. Keep it out of `.tmp` cleanup and ordinary downloads; redact paths from public job errors. Root should adjudicate this precise spelling/descriptor scope before dispatch.

### Ordinary commit and rollback

Prepare exclusive backups of old video **and old report**, plus explicit absence flags, outside shared locks while active mutation gates exclude cooperating writers. Same-filesystem hard links are a cheap option where safe, but preserve a copy fallback for unsupported filesystems; never move the old final away merely to prepare rollback. Large copying/hashing is outside locks. Private report permissions remain 0600. If report and video live in separate directories, prepare each stage/backup beside its own final; no cross-device rename assumption.

The final hook takes report lock, validates exact live job/operation/Event and prepared old-path identity, then performs only short replacement/rollback actions and state assignments. If identity changed while backups were prepared, abandon or prepare again outside lock; do not copy under lock. Out-of-process writers are outside existing web coordination and remain an explicit limit. In-process CLI calls targeting the same live web job directory are also uncoordinated.

| Prior pair | Failure during video replacement | Failure during second/report replacement |
|---|---|---|
| old video + old report | finals unchanged; remove stages/backups after owned cleanup | restore old video; report is old if replacement failed before effect; conservatively restore any changed member using backups |
| old video only | same; report stays absent | restore old video, remove newly created report if needed |
| old report only | same; video stays absent | remove newly installed video, restore old report |
| neither | both absent | remove newly installed member(s), restore absence |

Track successful mutations, not only where an exception was raised, and test real `os.replace` failure semantics at each exact destination. If rollback succeeds, rethrow the original publication error, retain old `job.output`/prior-file state and publish ordinary `error`. If restoration/unlink itself fails, raise an explicit delivery-recovery error carrying primary and rollback diagnostics and retain every artifact still needed to restore either original. Set web phase `error` with a recovery-required indicator; do not acknowledge `done`, relabel it a clean cancellation, or advertise the changed pair as valid. Existing active/lifetime gates persist through cleanup. After cleanup, a small private recovery-required gate must reject render/edit/tracker admission and output/report/compare access that would treat the unresolved pair as trustworthy. Status remains readable; vault can encrypt recovery files normally. Deliberate user delete is still governed by existing lifetime policy, not permanently blocked by a leaked lease. Rehydration must recognize that explicit failure descriptor instead of setting `done` solely from `output.mp4` existence at 4515–4525. This is recovery visibility, not automatic crash repair or a new export feature.

Retain backups until pair commit **and web success state** complete. An ordinary exception before durable state acknowledgement rolls back while holding the same reader exclusion boundary; after commit success, incidental later log/progress callback errors must not produce a fictitious failed/cancelled render with a successfully committed pair. Move fallible completion logging before commit or define it as nonauthoritative after commit. The later `_run_job` success block at 1093 must stop independently revalidating/assigning success for the new hook: otherwise a cancel can invalidate the owner in the gap. Store a local committed outcome so expected postcommit cleanup does not overwrite terminal success. Success dict assignments must be part of the transaction, with rollback of any partially assigned terminal fields if an ordinary failure occurs there. No promise for MemoryError/process death between arbitrary Python assignments.

Two final replacements plus rollback are ordinary exception safety, not a process/machine-crash atomic pair. No directory-fsync/durable restoration claim, database, global transaction registry or generation archive is proposed.

Do not create an extended-real/custom-number abstraction, special non-narrowing comparison system, general iterable protocol or promise Fraction/Decimal/extended precision solely for hypothetical embedders. Retain useful ordinary NumPy support without whole-array truth tests or gratuitous array/document copies. A standard scalar finiteness check plus narrow conversion/arithmetic exception handling is sufficient where it preserves supported inputs. Actual arithmetic/conversion overflow, including a nominally finite input too large for the existing calculation, may fail with the safe field/detection/frame diagnostic; G need not extend the numeric range. ### P: optimistic output-frame validation is the smaller choice

For the current output-frame endpoint, an optimistic publication epoch is sound **within managed in-process publication**, provided every relevant final-path mutation participates and the returned frame is detached before revalidation. It does not require holding a lock through native decode, a reader counter, a pending-commit gate, a long-reader reservation subsystem or an arbitrary-path registry.

Use a monotonically increasing Python integer in the existing stable `_JobFiles` state (lifetimes.py:10–21), initialized for new/rehydrated live jobs and never persisted as report data. While holding the same report lock as final publication, increment it **before each attempted managed final delivery mutation**, including video/report replacement, restoration replacement and absence-restoring unlink. Even a failed replacement attempt conservatively invalidates an overlapping frame. Never restore the old epoch when rollback restores identical bytes/path; incrementing through successful rollback prevents ABA. Keep pair commit and rollback under the report lock, as already required. No reader can capture an epoch in the middle of those operations. If a different managed writer can mutate the same final video, it must use this boundary too; wrapping only the successful final hook is insufficient.

Proposed `job_frame_at?src=output` flow at web:1661–1685:

1. Keep its existing request FILES ownership, acquired before report locking at 1180–1201. Under the stable owning job's report lock, check live identity/recovery status and capture `(job/state identity, output epoch, selected source identity/path)`. For this endpoint select `job.output` under that lock. Preserve the existing fallback to `_job_video(job)` when no output exists, but record that the fallback was selected; do not silently switch paths during one attempt.
2. Release the lock, construct `VideoCapture`, perform the existing timestamp/backoff reads, and release it in finally. Decode and JPEG encoding remain outside shared locks. Keep the actual detached frame/JPEG or a captured open/decode failure pending validation. Constructor failure must also take the validation path; do not emit a transient 404 before checking whether publication overlapped.
3. Reacquire only the owning report lock, recheck live identity/recovery status, selected output/source identity and epoch. If unchanged, return the detached result or the normal stable-source error. If changed, discard **both** pixels and any transient decode error. Retry the complete capture/decode/revalidate flow once against the current source. After two changed attempts, return an explicit stale/conflict response such as HTTP409 `output changed during frame read; retry` rather than returning unverifiable pixels or retrying without bound. A recovery-required state is its explicit failure response, not ordinary staleness.

A commit after the successful final revalidation can coexist with returning the already detached older image: that revalidation is the response's linearization point. This endpoint does not promise newest-at-transfer completion or consistency with another HTTP request. A commit/rollback overlapping native open/read always changes the epoch, even when the path and restored file bytes look identical. A same-path generation check, `job.output` comparison or stat tuple alone is insufficient for that ABA schedule.

This mechanism **detects and discards** an overlapped read; it does not physically pin the decoder's inode or make a failing backend open succeed. It is sufficient for returning a verified single managed generation because an accepted attempt spans no managed final mutation from source capture through detached-result validation. Concrete remaining risks are omitted mutation sites, uncoordinated external/direct-CLI writers, filesystem/symlink changes outside existing admission guarantees, and a native decoder call that never returns. Epoch validation cannot interrupt native work. On Windows an opened decoder may instead prevent publication; P's ordinary replacement/rollback error contract still applies, followed by epoch rejection if a mutation was attempted. No new platform claim is established here.
