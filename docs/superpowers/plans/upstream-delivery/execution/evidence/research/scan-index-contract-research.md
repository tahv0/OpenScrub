## Proposed implementation brief 1: P11C reverse candidate discovery

### Existing authoritative behavior

`openscrub.py:7096–7127` owns the entire reverse pass. It visits scans and words in supplied order; there is no chronological sort and equal timestamps/duplicate words remain separate observations. For each word:

1. Normalize using exactly `PhiMemory.norm` (`786–787`): strip the specified outer punctuation and lowercase. Do not introduce whitespace, internal punctuation or digit normalization. Normalized words shorter than four characters or in STOPWORDS are skipped. The allowlist check is on the original word and applies before memory lookup (`7105–7109`). Confidence does not gate reverse recall.
2. Walk `memory.items.items()` in dict insertion order. Skip categories outside `cats`, then skip keys for which `memory._gated(k, cat)` is `None` (`7110–7114`). Immediate categories recall at once; other categories need the primary count threshold (`762–764`, `806–813`). The source's comment says separate scans, but `add` increments per call, not by distinct timestamp (`803–804`); do not change that behavior here.
3. If either string is `str.isdigit()`, both must be digit strings of the same length with at most **two** unequal characters (`7115–7117`). Unicode `isdigit` semantics and the existing character comparison must survive. Otherwise require length difference at most two and `fuzz.ratio(k, n) >= lenient` (`7119–7120`). There is no partial-ratio match here.
4. The **first eligible matching key** wins, regardless of score or whether a later key is an exact match. Append exactly one new Detection for the word and stop that memory walk. Its text is the original OCR word, category is the winning remembered category, box coordinates are converted with `int`, confidence with `round(float(conf), 3)`, and offset with `tuple(cum)` (`7122–7125`). Other fields retain dataclass defaults (`730–751`). Preserve output scan/word order, duplicate records, conversion failures and all fields.

Memory `add` ignores face/manual, stores the first category for a normalized key, and increments counts on repeated primary adds (`789–804`). Re-adding a key does not move its insertion priority. A later category supplied to `add` does not replace the original category. This matters for ambiguous words and category filtering.

**Forward recall is not a substitute.** It admits length-three exact/numeric input, uses at most one numeric mismatch, uses `memory.threshold` rather than reverse `lenient`, and chooses a fuzzy winner before applying the sighting gate (`815–849`). Its exact shortcut can also hide an earlier eligible fuzzy candidate. Reusing its private `_alpha`/`_digits` caches is not automatically safe for a reverse-only change: those caches represent `add` history, whereas the current reverse owner reads the actual `items` mapping, including any ordinary caller's pre-call changes. Avoid a global PhiMemory rewrite or a batch scorer change in this brief.

### Smallest supported index and fallback

Build a **local, per-reverse-call** index from the actual insertion-ordered `memory.items`, assigning its own insertion serial. Store digit-string and other-string buckets by exact length, retaining `(serial, key, category)` references in bucket order. For a digit query, discover only the same-length digit bucket. For a non-digit query, discover the non-digit buckets at lengths `len(n)-2` through `len(n)+2`, in one globally ascending insertion-serial stream. A bounded k-way merge of at most five ordered buckets can retain order without sorting every query's concatenated candidates; a single numeric bucket already has the correct order. Do not process length buckets in numeric length order.

Run the existing category, gate and matching predicate on every discovered candidate. Do not preselect the highest score, take an exact shortcut, filter after choosing a winner, change leniency, or call forward recall. Candidate discovery is a conservative superset of possible hits: numeric mixed-type/different-length strings cannot hit, and alpha keys outside the ±2 range cannot hit, independently of threshold. If using ordinary `add`-constructed memory, key length starts at three; the index need not assume this when reading the actual mapping. A three-character remembered alpha key can match a four-character reverse query.

The optimized domain must be explicit: ordinary stable PhiMemory state, plain string keys/categories and ordinary pure category/gate/allowlist behavior. A local snapshot must observe pre-call dictionary changes and be rebuilt each invocation; it must not persist after finalization. Empty input/no eligible words should not require unnecessary construction. Lazy first eligible-word construction can avoid that cost while leaving scan/word order intact.

Unsupported mappings, nonstring keys/categories, overridden or side-effecting gates/allowlist/category containers, or memory mutated during lookup require the original traversal rather than silent omission or eager new errors. Ordinary `_gated` is pure, but skipping it for impossible-length keys can otherwise change a custom gate's effects/errors. A fallback must preserve old exception timing and prior output/mutations for unsupported inputs; do not catch an error from malformed input and return a successful empty result. Eligibility detection itself must not eagerly apply string operations to malformed keys or consume/reorder a one-shot `scans` iterator. Concrete dispatch cost and how to recognize supported state remain an implementation decision to validate; if safe dispatch costs erase the gain, do not adopt. No unsupported-input acceleration claim follows from this report.

Construction traverses M remembered entries once and retains O(M) references/serials plus bucket metadata until the call returns. Lookup emits C candidates per word instead of M, with a small merge-order cost. It does **not** make similarly sized strings constant-time. Dense same-length memories, repeated content with an early winner, tiny/empty histories or few eligible historical words can yield no benefit or a regression. An index that merely replaces repeated length checks with bucket construction but leaves all relevant keys eligible needs a measured cost gate.

## Proposed implementation brief 2: P11D merge candidate discovery

### Existing authoritative behavior

`openscrub.py:2915–3055` is the full boundary. `sorted(dets, key=t_start)` is stable (`2925`): equal starts retain input order. Do not sort by category/box/text or normalize unsupported timestamps. The original Detection objects are retained and mutated; this is not a pure record transformation.

For every sorted detection, `last_seen` is reset to its start (`2966`). Dense detections are appended directly to `merged`, retain their short original end, and never enter `mergeable` (`2967–2969`); the dense checks later in the candidate loop do not justify adding dense entries back. Every non-dense detection has its own `t_end` overwritten with `t_start + hold`, even if it is subsequently absorbed (`2970–2976`).

`reversed(mergeable)` visits prior **region creation/birth order**, newest first (`2977`). A successful merge does not move the winning region to the end. This is not order by most recent `last_seen`. Category must compare equal and `boxes_overlap` must pass (`2978`). The overlap function uses **inclusive slack 12** in both axes (`1327–1329`): equality at the slack boundary overlaps; it is not IoU, positive-area intersection or a distance-to-center rule. Coordinates are content coordinates and may be negative.

When `fuzz`, `m.text` and `d.text` are all truthy, normalized full ratio must be at least 70 **or** partial ratio at least 85 (`2989–2994`). Empty text bypasses this gate; `fuzz=None` bypasses it entirely. Partial matching permits a short substring inside a much longer string, so exact-text, text-length or first-character buckets are not safe exclusions. A text index may only be used after proving a complete superset for this actual OR predicate, including its bypasses.

The temporal predicate uses `d.t_start - m.last_seen`, not `t_end` (`2995`). Gaps `<= hold` pass directly. Larger gaps must first avoid contradiction; gaps `<= bridge_gap` then pass, while still larger gaps can pass visual `gap_check` (`2996–3005`). Thus no fixed age window or retirement by `t_end`, hold, bridge gap, track, person or text identity is justified. A false/contradicted recent candidate can be skipped in favor of an older candidate; enumeration must retain the original order and callbacks.

Contradiction is ordered scan evidence strictly inside `(t_from + .01, t_to - .01)` (`2940–2942`), confidence at least .6, word center within the current union box plus horizontal 6/vertical 4 margins, and repeated normalized divergent text length at least three (`2943–2962`). Two equal readings can be in duplicate timestamp entries, even in one scan's word list; there is no distinct-scan counter. With fuzz, ratio >=70 or partial >=85 means the same text; without it `same=False`. A single divergent read does not contradict. Do not index/rewrite this predicate as part of P11D.

On success only the winner's `last_seen`, `t_end` and union box change (`3007–3010`); its start, category, original text, confidence, anchor, track/person/poly and identity survive. The absorbed input still had its own last_seen/end changed before the search. On failure, append the same object to both result and searchable history (`3012–3014`). An index must never hash mutable Detection objects or deduplicate equal-but-distinct inputs. Repeated object references require fallback or explicit alias-safe handling: changing one alias may change another retained entry. Preserve all input-object mutations as well as returned records.

Tail extension runs after candidate merging over `merged` in result order (`3026–3054`), using the final union box and original region text. Its .01/bridge/confidence/support stop rules remain owned by P11B. Reordering merge output or stale union boxes changes that behavior even if the number of merged records happens to match.

### Minimum safe variation: category partition, conditionally useful

Keep the authoritative `merged` result and stable sorted detection loop. Maintain insertion-ordered lists of **non-dense region entries by category** and query the current category's list in reverse. Append a region only when the existing loop's `else` creates it. Never move it after a successful merge. Retain the original category/overlap/text/gap predicate unchanged. Category discovery can exclude exactly those entries that the first predicate would reject, without caching a fuzzy result or replacing geometry.

This requires hashable, stable ordinary string categories and ordinary stable detection metadata. Unhashable/nonstring categories, unusual equality, aliased mutable objects, or callbacks that can change categories/other candidates need a semantics-preserving original-loop fallback; do not introduce a new `TypeError` by hashing an input that formerly only compared for equality. No sorting/cleanup of malformed times/boxes/scans is authorized. A custom `gap_check` may have observable call order or mutate objects: accelerated enumeration must either prove its stability contract or fall back, not assume every callback is the read-only ordinary closure. Dispatch must keep the actual `run_scan` closure usable if a fast path is adopted; an unsupported-callback guard that disables every ordinary scan has no product benefit. Exact guard mechanics remain a cost/design decision for the future implementer.

Incremental category construction retains O(M) references to searchable regions, plus dictionary/list metadata. It removes cross-category loop/predicate visits; it does **not** remove cross-category `boxes_overlap` calls because the current OR condition already short-circuits before geometry. In a single-category history its candidate count is exactly unchanged. Therefore **do not adopt category-only indexing as a fix for the completed unique-email probe**. A mixed-category result may justify investigation but cannot be represented as a resolution of that demonstrated trigger. This rejects that variation for that claimed benefit, not all P11D possibilities.

### Spatial extension: safe discovery contract, adoption deferred

If representative source-owned geometry cost warrants further work, a separate local per-category spatial broad phase may conservatively return candidates whose **current union boxes** could overlap. An explicit small candidate is a sorted left-endpoint structure with stable birth serials: query entries with `m.x1 <= d.x2 + 12`, retain those with `m.x2 + 12 >= d.x1`, then restore descending birth serial before running the unchanged full predicate. Inclusive comparisons preserve the exact slack boundary. The y test may remain in authoritative `boxes_overlap`; broad-phase false positives are acceptable. False negatives are not.

Every union that decreases `m.x1` must update its endpoint position before the next query; `m.x2` must be read from the current object or updated too. Keep equal endpoints distinguished by birth serial. An older region's update does not give it a newer birth serial. Invalid/nonfinite/degenerate boxes and unsupported alias/callback mutation need the original complete traversal rather than pruning based on ordering that no longer holds. Scans need not be chronological for this candidate-discovery variation; their original contradiction/tail traversal must remain untouched.

This concrete structure is a research option, **not a recommendation to implement it regardless of cost**: a stdlib sorted list has O(M) insertion/removal shifts; a query can scan an O(M) left-endpoint prefix and then sort C emitted entries, O(C log C). Many aligned/large/overlapping boxes leave almost all candidates eligible. Count endpoint-prefix visits, sorting, maintenance and fallback work, not just the final candidate list. If that duplicates the existing geometry work, close that variation without production code. A more complex 2D/grid/tree index is not justified by the present source/work-count evidence and needs its own bounded maintenance/retention rationale; any overflow route must include all potentially matching candidates. No arbitrary history window, similarity threshold or per-category cap is allowed.

## Decisions still requiring evidence

P11C's necessary-condition length/type buckets are source-supported, but their dispatch, construction and serial-merge overhead versus real heterogeneous/same-length histories are unmeasured. P11D's category partition is source-supported only for stable ordinary categories; it has no candidate-count benefit for the demonstrated all-email history. A dynamic spatial broad phase could narrow that different predicate, but stale union entries, ordering restoration, list maintenance, callback/alias support and dense overlap can erase or invalidate the benefit. These are explicit open decisions, not reasons to claim that every P11D index is impossible. Neither report section establishes general long-video/4K performance, a memory ceiling, changed confidence policy, or an inference/preview speedup.
