## Recommended identity: one current generation, no report tree retention

Use private `_JobFiles.thumbnail` state, or an equivalent state owned by that same live job. It contains only the current immutable generation descriptor, bounded in-flight tickets, current JPEG entry metadata and retired-file cleanup tickets. It never enters reports/options/public job JSON. Give each new or rehydrated live job an unpredictable incarnation nonce; restart/unlock rehydration must not resurrect an old generation or pending builder.

A generation descriptor has these exact inputs:

- `job_incarnation`, monotonic thumbnail invalidation epoch and captured `files.operation` object identity. A user save does not change P06 operation identity; successful report publication still changes the thumbnail epoch. Queue/retry/render admission and cancel acknowledgement invalidate pending thumbnail work through the same report-lock boundary. Cancellation does not erase the last committed report; a later read may establish a new read generation against that report and the new fence token.
- Canonical **selected scan/preview source**, including normalized SDR/CFR selection where used, a source-selection epoch, verified file stamp and source-content digest. The original upload hash or a provenance pathname alone does not identify the decoded normalized file. Cache a digest only against the verified source stamp within this live job; compute it once on a newly observed source identity, not for every row/report save/warm hit.
- Opened report file stamp plus digest of its **complete raw bytes**, and a successful parse/schema validation of the crop inputs. A coarse whole-report digest/epoch safely includes row order/index, full-precision `t_start`, `t_end`, `last_seen`, `cbox`, fps, complete cum, and other render/source state. Do not derive identity from rounded metadata timestamps. This intentionally invalidates decision/text/audio-only saves too. No per-row source geometry index is needed.
- A private format/recipe version covering candidate-time order/clamping, frame-index selection and bounds, decoder/frame selection policy, coordinate conversion/rounding, crop clipping/padding24, blank predicate/std threshold8, outline color/placement/thickness, JPEG quality80 and any future scaling/color/rotation/transformation setting used by this path. Full-frame detframe has its own recipe discriminator (expanded outline and JPEG84), sharing the generation fence. Include an implementation/runtime discriminator when a deployed decoder/encoder or transform choice changes output; process incarnation already avoids cross-restart reuse. Merely changing a source filename is insufficient.

Define opaque `V = digest(process/job nonce, epoch, operation-fence token, selected-source identity+digest, report identity+digest, recipe versions)`. Never serialize Python object addresses, paths or report content into public URLs. A generation nonce plus an in-memory descriptor binding all these inputs is also sufficient; the version need not be recomputed by the browser. Files use fixed-prefix validated hex token and nonnegative integer row: `thumb3_<V>_<i>.jpg`. Resource identity is `(V, kind, i)`, where kind distinguishes crop/detframe. Do not allow a caller-supplied token to become an arbitrary path.

Whole-report hashing occurs only while establishing a newly observed report generation (and can stream alongside its cold private parse). Source hashing occurs only for a newly observed source stamp. Both happen outside locks while owned. A warm verified generation requires constant-size checks and JPEG reading, **zero report opens for content, zero JSON parses and zero full report/source hashes**. Small `stat`/`open`/`fstat` checks are allowed. Generation discovery may parse; do not call that an already-verified warm hit. Once a cold request finishes, discard its private report tree. Metadata may parse again, and different cold indices may still parse independently; P08B owns measured immutable parse reuse.

### What file identity proves

Use canonical path plus the opened regular file's device/file-id or inode, size, available `mtime_ns` and `ctime_ns` (and a managed publication/source epoch). Compare path stat with opened-descriptor fstat at selection and again after read/hash/decode and before acceptance. Atomic replacement with unchanged size/mtime normally changes file-id/inode; in-place equal-size updates normally change modification/change times. This covers the prior reproduced replacement without relying on size+mtime alone. Verify the JPEG's own saved stamp/size as well; unexpected mutation/corruption invalidates that entry rather than sending unverified bytes.

A stat tuple is **not a cryptographic proof of unchanged contents**. Coarse timestamps, inode reuse, Windows ctime semantics, network filesystem caching, external in-place writes/ABA replacement and a writer deliberately preserving every observable field can evade it. Source hashing once per observed stamp does not remove this limitation. Nor does `cv2.VideoCapture(path)` expose a portable verified descriptor for all platforms: compare its pinned canonical pathname/stamp before and after decode, and explicitly limit concurrent external mutation guarantees. Hashing every warm input would violate the requested cost contract and still would not create a cross-process transaction with an uncooperative writer.

For filesystems without usable change/file identity, do not silently assert verified warm reuse: use a declared conservative mode that revalidates content on each access (losing fast-warm benefit), or refuse the unsupported concurrent-mutation mode. The supported fast contract is managed in-process publication plus observed external replacement/change on a filesystem with reliable stamps, not arbitrary concurrent external writes. A coordinated external writer should atomically replace files while no current reader/worker mutates the job, or use a separately specified protocol. Windows/network runtime evidence is still required.

If an observed report identity changes, invalidate the old valid generation **before** validating the replacement. Parse/shape failures produce a current-report error, never old JPEG200/304. Keep only a small failed-identity marker to prevent repeated speculative validation flights; a changed identity or an explicit later request can retry. A failed managed atomic publication, by contrast, does not advertise a new committed identity. Missing report/source is404/410 according to existing lifecycle meaning; invalid current report is a structured5xx error with `Cache-Control: no-store`, not stale success.

## Publication, source selection and lifetime order

The order is **P06 admission/reservation first, then report lock, then release the report lock before any lease release**. Never acquire `VAULT_LOCK`, follow/reserve a related source, release a lease, wait for a worker/fill, hash, decode, transfer a response or perform long reads inside `report_lock`. Short stat/open/fstat and final rename/metadata assignment are coherent selection/publication operations; they have OS/filesystem latency limits, not a hard wall-time guarantee. Existing P06 report transaction serialization/fsync is not being redesigned by this recommendation.

1. **Prepare ownership outside the report lock.** Reserve the live job and actual canonical source/containing job under existing `VAULT_LOCK` admission. Metadata generation discovery now needs source ownership too: add `job_detections` to source-consuming admission (or explicitly prepare a child source lease before selection). Demand/detframe already have it. Background pre-generation gets its own lease before thread start; every start failure/finally releases it exactly once.
2. **Select coherently under `report_lock`.** Call `_report_current`; compare admitted source, selected source epoch, live job incarnation, current operation and pending-source state. Open/fstat the current report and source identity while this boundary holds. A source lease captured before a source change is insufficient: reject/reprepare outside the lock. Capture one candidate descriptor/ticket; do not perform JSON parsing, digesting or decoding here. An existing verified current record with matching epoch/stamps can take the warm path.
3. **Validate generation outside locks.** Read/hash/parse the opened report generation and hash a newly observed source while leases protect all job trees. Validate required fields: finite positive fps, nonempty/valid offsets, finite row coordinates/times, bounded row index and usable spans. Check before/after descriptor stamps; unchanged path alone is inadequate. Reenter report lock, recheck every fence/stamp and publish the tiny descriptor only if still current. Discard candidate tree/handles on every refusal. There is at most one generation-discovery flight per job; contenders wait outside locks with a bounded deadline or return pending409.
4. **Build a crop outside locks.** From the verified report generation construct the same row recipe for demand/pregen. Decoder is pinned to that selected source. Encode into a private0600, fixed-prefix `.tmp` file in the job directory; complete/flush/close it before publication. Hash encoded bytes for ETag here. Check encoder/write failures, do not count a failed write as a warm hit. The builder's lease survives through source decoder close, staging cleanup and ticket removal.
5. **Accept under `report_lock`.** Revalidate exact incarnation, generation object/epoch, current operation token and cancellation status for that captured operation, selected source and report/source path+descriptor identities. If the ticket was invalidated, discard; an Event cleared elsewhere never revives it. Atomically replace the target only for that exact key. An already accepted complete artifact wins; a late equivalent builder must not overwrite it with a different body. Never publish new pixels at an obsolete requested `V`.
6. **Serve coherently.** While holding report lock, validate current `V` and open/fstat the accepted JPEG. Read its small body outside locks, close the handle, then revalidate the same generation before sending200/304. For the smallest implementation, return detached JPEG bytes rather than retain a thumbnail file handle for a slow WSGI stream; the existing P06 detached-response lease rule then applies. A lock/cancel after this acceptance cannot recall already materialized response bytes, matching normal P06 request linearization. If retaining `send_file`, open/metadata/body must refer to one descriptor, and its lease/retired-file reader ticket must last through iterator close; do not reopen a pathname after dropping the lock.
7. **Cleanup outside locks, still owned.** Close decoder/file handles, discard every rejected stage, release pending/reader tickets, remove retired artifacts, and only then release the lifecycle lease outside `report_lock`. No waits/joins while holding either mutex.

An explicit version request gets **zero automatic generation substitution**: mismatch returns409 `{"error":"thumbnail_obsolete","refresh":"detections"}` with no-store. Generation churn during its build also returns409; it must not retry decoding against a new generation under the old URL. Unversioned compatibility callers may reselect at most once (two total selections), then409; there is no unbounded retry recursion. A generation flight has a bounded wait (proposed one second; timeout returns409 `thumbnail_pending`), not indefinite waiter ownership. One pending build per `(V,kind,i)` may coalesce demand/pregen; on contention return pending or wait once outside locks. This is duplicate-publication protection, not P08B shared report snapshots or P09 prioritization. Pre-generation stops on its first obsolete ticket and does not autonomously restart forever.

### Required changes to existing publication/source APIs

P06 currently provides lifetimes and a report lock but **does not provide thumbnail notifications or source-selection transactions**. Make these specific additions part of P08A's declared integration surface:

- After each successful `atomic_report` in engine checked publisher, sparse save and tracked append, call a tiny `thumbnail_report_committed_locked(job)` while still under that job's report lock. It increments the epoch and retires current descriptor/artifacts/tickets. No hashing, parsing or file deletion in the notification. All failed serialization/fsync/replace paths skip it. A non-writing no-op response need not change the epoch.
- `_update_job_source` currently assigns `job['video']` under `VAULT_LOCK` only (444–456). Split preparation/reservation from commitment: reserve the new containing source under VAULT, release VAULT, then under report lock revalidate job + expected worker operation + prior source, assign canonical path/source epoch and invalidate thumbnails. On failure, release provisional child ownership **after** leaving report lock. No report→VAULT nesting. Keep source ownership with the worker throughout its follow-up report/provenance access.
- Scan report commitment must close the report/source-pair gap. In the checked scan publisher, mark the thumbnail pair pending when the new report commits; outside report lock prepare/select the normalized source from that **same constructed scan document**, then commit source and clear pending under report lock after operation validation. Until then metadata/crops return pending409 rather than publish pixels against old source/new report. Do not reread an unrelated future report to select normalized input. Alternatively pre-prepare selected-source ownership before report commitment and atomically publish both identities under the report lock; do not acquire VAULT from the publisher. In either variant pre-generation launches only after pair readiness, with captured scan operation/generation/source.
- `_begin_operation`, cancel acknowledgement and deletion invalidation retire thumbnail tickets using the same report-lock ordering. `_pregen` must capture/compare its creating operation even though its own lease is not the P06 pipeline owner. Do not simply call `_operation_valid` with its current unbound lease and assume it is fenced. Source/report epoch changes also retire it, independently of Event status. Ordinary request tickets may establish a fresh generation after cancellation; old background tickets may never adopt it.
- Metadata selection, warm file open and final fill acceptance all use the report-lock wrapper. Source-owning request admission must compare a captured source to current source rather than trusting `_job_video` alone. Preserve fresh transaction documents and existing report download open/metadata coherence.

This is the minimum missing source API change, not a recommendation to add another registry, global cache lock, parallel owner counter or cross-process lock service.

## HTTP and ordinary browser contract

Extend GET detections with `thumbnail_version: V`; every returned row gets a `thumbnail_row` fingerprint suitable for **equality only**, calculated while its private metadata document exists. Fingerprint the complete raw row, not its rounded projection/group representative, so equality proves the displayed row has not changed within the documented digest assumptions. This is not a permanent row ID or a way to migrate indexed drafts across reordering. Metadata response and V must be finalized against one verified report/source generation; revalidation failure returns bounded409, not mismatched JSON/V. Keep metadata no-store.

Use `thumb/<i>?v=<V>` and `detframe/<i>?v=<V>` for both normal/zone-dropped cards and lightbox. For successful versioned responses choose **`Cache-Control: private, no-cache, max-age=0, must-revalidate`** and strong `ETag = hash(kind,V,i,encoded JPEG bytes)`. This retains conditional body savings while allowing every revisit to reject obsolete generations and vault access. Check current generation/lifecycle **before** accepting `If-None-Match`; old ETag cannot produce304 for obsolete V. Avoid Last-Modified as an authoritative validator (omit it or never let it override version validation). Use the same header policy on304. This conservative policy avoids intentionally extending sensitive-image freshness; immutable long-lived HTTP storage is not necessary merely because URLs are versioned. No-store unversioned responses, errors and obsolete/pending responses; legacy `?r=` must not select a distinct generation or extend freshness. Already cached old3600 responses cannot be remotely revoked, but the newly served no-store HTML uses new versioned URLs.

Keep ordinary `<img>` loading and existing lazy attribute. No priority queue, visibility observer, abort scheduler, Blob URL fetch pipeline, workbench mode or save protocol is needed. Since img.onerror does not expose HTTP status, handle any image failure as follows:

1. Capture `{jobId, VIEW_GEN, displayed V, row index, displayed thumbnail_row, image node}`. Mark the image unavailable. One per-view/per-displayed-generation Promise may perform one no-store detections GET, shared across all failed images. Set the attempted marker **before** the fetch; keep it set after network/404/corrupt/pending failures. No timer that clears it automatically, and no timestamp retry.
2. On completion require `ownsView(id,gen)`, same displayed V and still-connected original node. A late response from A→B→A or a removed review cannot alter current UI. If metadata fails or returns the same V, leave the placeholder/error; no second fetch for that observed generation/error. Do not retry for missing row or decode errors.
3. If V changed, patch only image URL/version bindings for rows whose **same index and complete raw-row fingerprint remain equal**; capture the new V in that lightbox binding too. Leave changed/missing/reordered rows unavailable with a short “Review changed; reopen review to refresh” message. Row fingerprints may change after a legitimate geometry save; refusing an automatic card rebinding is safe. Intentional reopening normally constructs the current cards. Do not silently transfer dirty indexed choices to new rows. A source-only change or unrelated report edit can update equal rows without touching the editor.
4. That automatic refresh attempt has a single budget for the current mounted review: the patched generation does **not** replenish it. If patched images also fail or another generation appears, leave placeholders until an explicit reopen/retry action. Reset on a user-initiated review open/view change, not on an error, metadata response or save acknowledgement. This bounds the chain as well as duplicate failures at one V. Opening a lightbox may share this budget; failure leaves an unavailable image, not a loop.

Only thumbnail identity and src attributes change during this recovery. **Never call `loadReview()`, `showPanel()`, `openJob()`, `trimReviewDraft()`, or `loadBoxEdit()` from thumbnail recovery**: `loadReview` removes/recreates `#review` and its editor slot. Leave `EDITS`, `REVIEW_DRAFTS`, EN/MAN, manual IDs, audio/audioSaved/audioLoaded/audioInFlight, BE object/selection/playback and any in-flight save references untouched. Do not synthesize a successful save, auto-save, invoke render, or make a successful save trigger a metadata/save feedback loop. A normal explicit save-and-render continues through P07a's existing acknowledgement logic. If updated row bindings are incompatible while drafts are pending, retain those drafts and display the stale-image status; row-draft reconciliation is a separate problem. Browser tests must cover this refusal as well as source-only URL refresh.

## Derived-file cleanup and module boundary

Keep only current-generation disk JPEGs plus files still owned by an already admitted reader/stage cleanup. On invalidation mark old generation inaccessible immediately under report lock; detach its cleanup list, cancel builders and remove old JPEGs outside locks under the same job/store lifetime. POSIX can unlink an open old file; for Windows defer unlink until that exact reader closes. Never remove a file merely because its row index matches: include captured generation/path and avoid touching newer artifacts. Startup/rehydration removes legacy `thumb2_*`, orphan thumbnail `.tmp` and noncurrent `thumb3_*` before reusing any derived state; it does not reconstruct a generation history from them.

Keep no permanent source/report/row sidecar, plaintext database or generation catalog. Current stamps/digests/ETags are in-memory and evicted on job removal, successful vault transition/recovery rehydration and incarnation replacement. Vault/delete still refuse active leases; once admissions close and users drain, evict descriptors before encryption/removal. Cleanup workers require real ownership and may not recreate files after that boundary. No promise of secure heap erasure or revoking previously delivered browser bytes follows from dropping references.

Bound file retention explicitly: one current generation; retired files only for live readers or **one bounded cleanup backlog**, not one retained directory per revision. Proposed cleanup retries are three bounded attempts plus final reader-close/next normal lifecycle sweep. If deletion still fails, mark cleanup blocked and refuse additional cache materialization/epoch disk accumulation until it is cleared; current requests may return detached uncached pixels only if generation validation succeeds. Do not endlessly append failure tickets or ignore unlink errors. Each staging operation has an unconditional finally; pregen has at most one worker per job and stops when superseded. This is bounded cleanup, not a promise that an OS permission error can be repaired automatically.

A private `openscrub_internal/thumbnails.py` **earns a coherent boundary** if it contains only generation/file stamps, immutable recipe values, crop/encode staging, per-key fill/reader tickets and retirement cleanup shared by demand/pregen. Web adapters retain Flask errors/responses, P06 admission/locks, registry/operation checks and source preparation; the helper must not import web globals or own another lifecycle protocol. Useful narrow methods are `invalidate_locked(reason)`, `select_locked(owned_source, operation)`, `validate_candidate(candidate)` outside locks, `accept_generation_locked(candidate)`, `stage(recipe, source)`, `accept_jpeg_locked(ticket, staged)`, and `cleanup(retired)` outside locks. Packaging already includes the whole `openscrub_internal` directory in wheel/sdist (`pyproject.toml`) and copies it into all three Docker images (Dockerfile63, Dockerfile.cuda135, Dockerfile.intel97). ## Design amendment — minimal generation identity without whole-input hashing

**This amendment supersedes the earlier requirements for full-video source digests, full-report byte digests, their associated hash flights/tests, and any proposed user-visible conservative rehash mode.** The historical baseline and pinned source evidence are unchanged. The recommended P08A identity contract uses an opaque generation nonce bound to managed epochs and coherent opened-file identities; it does not read an entire source video merely to name its first thumbnail.

A full-video digest computed once per observed stamp cannot strengthen the stated warm guarantee: subsequent warm reuse still trusts that stamp. An external writer that changes bytes while preserving every observed attribute remains undetectable on later hits. Conversely, the reproduced same-path/same-size/same-mtime atomic replacements are detected by changed opened file identity without hashing video contents. A full-report byte digest is likewise unnecessary merely to name an in-process generation: a fresh unpredictable nonce identifies that generation, while publication epochs and verified file stamps determine whether it remains current. Neither digest turns uncooperative concurrent external writes into a transaction. Removing both avoids a potentially multi-GB source read and an extra whole-report hashing pass, without weakening the explicitly supported guarantee.

The smallest descriptor is therefore:

```
Generation {
  opaque_nonce,
  live_job_incarnation,
  managed_report_epoch,
  selected_source_epoch,
  captured_operation_identity,
  canonical_selected_source_path,
  opened_source_stamp,
  canonical_report_path,
  opened_report_stamp,
  crop_and_detframe_recipe_versions,
  validated_current_report_generation
}
file_stamp = (device/file_id_or_inode, size, available_mtime_ns, available_ctime_ns)
JPEG key = (opaque_nonce, resource_kind, nonnegative_row_index)
```

`validated_current_report_generation` is a validity flag bound to the descriptor, **not a retained report tree or content digest**. Establish it by reading/parsing one coherently opened current report outside locks, validating crop schema, and rechecking its opened/path stamps and all managed fences under `report_lock`. Report parsing already needed for metadata/cold geometry supplies row/time/fps/cum/geometry; a successful managed report publication always advances the epoch even if replacement happens to reproduce the same observable stamp. New source selection, observed source/report stamp change, operation invalidation, incarnation change or recipe change retires the nonce before any new result is accepted. A changed/corrupt report cannot inherit the former validity flag. Distinct file stamps may represent identical bytes and still receive distinct nonces; harmless over-invalidation is intentional.

Source selection still follows the admitted actual normalized preview source, not an original-upload path/hash. Source open/fstat and pre/post-decode path comparisons remain; long video reads are only those needed for actual decoding. There is no full-source validation hash phase. Report and source descriptors may be opened in the brief coherent selection step, but no content read, parse or decode moves into either lock. Pending-generation deadlines, operation/source fencing, exact final publication checks and owned cleanup remain as specified above. The warm test now states **zero report parsing and zero full-input hashing on both cold generation discovery and warm reuse**; ordinary cold report parsing remains allowed. Remove full-input-hash pause schedules; retain selection/open/parse/decode/stage/accept interleavings and small JPEG-encoding/hash failure checks where applicable.

Retain **per-row content fingerprinting only for the browser's cross-generation equality check**. The browser needs evidence that the same displayed index still denotes the same complete raw row before patching its image URL while preserving indexed drafts. A server-generated generation nonce cannot answer that question across generations. Compute a deterministic canonical raw-row digest while metadata already owns its private parsed report; include the whole row so row-local geometry, timing, grouping and displayed content changes conservatively refuse automatic rebinding. Do not hash a full report just to obtain these row fingerprints, retain raw rows between requests, or treat equal fingerprints as permanent row IDs. Global fps/cum/source changes need not alter the row digest: they alter the generation nonce and thus the image URL; row equality only authorizes preserving the displayed row/draft binding. P08A may alternatively refuse every cross-generation automatic image patch and omit row fingerprints, but that sacrifices the already-described safe source-only/unrelated-row refresh. It must never patch by index alone.

A strong JPEG-byte ETag remains cheap and useful after encoding/read: it validates the actual small response representation. Its hash is distinct from a full-video/full-report generation-name digest. The nonce also separates crop and detframe recipe versions and all transformations through the descriptor, so complete generation identity does not require content-addressed filenames.

The supported external-change limit remains explicit: reliable file-id/change stamps detect the named replacement regressions, while unchanged-observed-attribute mutation, coarse/weak filesystem identity and arbitrary concurrent external writes have no new guarantee. Do not add a user-visible mode, configuration knob or fallback hashing policy in P08A. Document and test the supported filesystem behavior; on a detected incoherent selection/change, return the existing bounded pending/obsolete/error response and refuse stale success. Any stronger cross-process mutation protocol is separate work, not an implied property of an optional hash.

This amendment is a source-based scope reduction, with **no new runtime measurements or product changes**. The source manifest and baseline-results hash do not change; the static verification record additionally records the amended report hash.
